## 1. 目的と範囲
- SYS-FX012（凍結済みルール）を、GMOコイン外国為替FX で自動売買する。
- 対象は USD_JPY / EUR_JPY / GBP_JPY / AUD_JPY の4通貨。
- **やること**: シグナル検出、発注、ストップの管理（建値移動・トレール）、資金管理、撤退ライン、記録、監視。
- **やらないこと**:
  - ルールの変更・最適化（研究は minmax で行う）
  - 裁量の介入（緊急停止を除く）

## 2. 構成（Firebase、実行層専用プロジェクト）
| 要素 | 使うもの | 役割 |
|---|---|---|
| 起動 | Cloud Scheduler（5分ごと、各5分足確定の約20秒後） | `run_cycle` を1回呼ぶ |
| 処理 | Cloud Functions 第2世代（Python 3.12） | 同時実行は最大1インスタンス。1回の処理はおおむね30秒以内 |
| 状態・記録 | Firestore（asia-northeast1） | 足データ、判定状態、注文、建玉、日次成績、ログ、排他ロック |
| 秘密情報 | Secret Manager | GMO の API キー・シークレット（登録は司令塔。コード・リポジトリ・ログには出さない） |
| 監視画面 | trading-app-v2 にページを追加 | 実行層から読み取り専用の状況サマリを同期する（BTC の carry-executor-sync と同じ方式） |
| デプロイ | GitHub Actions（main への push で自動） | テスト合格時のみデプロイ |

- IP 制限（GMO の会員ページの機能）は任意のため、初期は使わない。有効にする場合は、Cloud NAT による固定IPが必要（月数千円）。
- API の制限: GET は1秒6回、POST は1秒1回（アカウント単位）。1回の処理で POST を連続させる場合は1秒以上あける。

## 3. 1回の処理（run_cycle）の流れ
1. **排他ロック**を取る（Firestore のトランザクション、期限付き）。取れなければ何もせず終了する（二重実行の防止）。
2. **緊急停止フラグ**・**撤退フラグ**を確認する。立っていれば新規は出さず、既存建玉のストップ管理だけ行う。
3. **GMO と突き合わせる**: 建玉一覧・有効注文・約定を取得し、Firestore の記録と照合する。
   - 次の場合は、GMO 側を正として記録を直し、警告を出す。
     - 記録にない建玉がある
     - ストップのない建玉がある
     - 記録にある注文が消えている
   - **ストップのない建玉は、最優先でストップを置く。**
4. **足データの更新**: 4通貨の5分足（BID・ASK、確定分のみ）を GMO の KLine から取得して追記する。1時間足は5分足から作る（左端ラベル、確定足のみ）。
5. **保有中の建玉のストップ管理**（§5）。
6. **新規エントリーの判定**（§4）と、資金管理のチェック（§6）→ 発注。
7. **記録**: 判定の根拠（ATR・ブレイク足・押し目・ストップ位置）、注文、約定、日次成績を Firestore に書く。
8. ロックを解放する。途中で例外が起きた場合もロックの期限で自然に解放され、次の回で突き合わせから再開する。

## 4. シグナル（minmax SYS-FX012 と同一。数値は minmax の凍結値を書き写す）
- 1時間足の N_BREAKOUT（1時間足の値幅 ≥ 3.5 × ATR(H1)）、H1 トレンドの判定不能は除外する。
- 急変フィルター: 同じ1時間足で4通貨中2通貨以上がブレイクしたら、落ち着いた1時間足が3本続くまで新規を止める。
- ブレイク足の確定後30分から72時間、5分足の押し目（ジグザグ 1.0×ATR(M5)、切り上げ／切り下げ）でエントリーする。
- 初期ストップ = 押し目の起点 − 0.703 × ATR(M5)（売りは逆）。
- 1イベント1ポジション。
- **先読みの禁止**: 判定には確定した足だけを使う（minmax の `bar_close_anchored=True` と同じ扱い）。

## 5. 決済・ストップ管理
- 利確なし。含み益が +1R に達したら、ストップを建値へ移す。以後は ATR(M5) × 0.703 でトレールする（5分足確定ごとに再計算し、有利な方向にだけ動かす）。
- **ストップは常に GMO のサーバー側に置く**（自前の処理が止まってもストップは働く）。
  - エントリーは成行、約定を確認した直後に決済の逆指値（STOP）を発注する。
  - 可能なら、IFD（新規＋決済逆指値）を一度に出す方式を採る。どちらにするかは T2 で確認して決める。
- トレールは、既存の逆指値の価格を変更（changeOrder）して行う。
  - 変更回数には注文ごとの上限がある（上限に達すると ERR-5206 が返る）。
  - 上限に達したら、取り消して置き直す。ストップのない時間が最短になる順序で行い、置き直しに失敗したら成行で決済する。
  - 無駄な変更を減らすため、最小の変更幅（例: 0.2 pips）未満の変更はしない。
- **週末の決済**: minmax と同じ時刻に、成行で全決済する。
- 最長保有時間（minmax の設定）に達したら、成行で決済する。

## 6. 資金管理（OBS000014 の本番設定）
- 1取引のリスク = 確定残高（円）× 0.5%。数量 = リスク額 ÷（エントリー価格 − ストップ）。
  - API の最小注文数量（現在100通貨）と刻み（1通貨）で切り捨てる。最小未満なら見送る。
- 1ポジションのレバレッジ上限 10倍、保有中の合計 10倍。超える分は数量を縮め、枠がなければ見送る（minmax `settle_trades` の shrink と同じ）。
- 当日（JST の暦日）の確定損益が −3R 以下なら、当日の新規を止める。
- 発注前に、有効証拠金・証拠金維持率を確認する（GMO の資産残高 API）。維持率が基準を下回っていれば新規を止める。

## 7. 撤退ライン（OBS000014 §4。自動で判定し、該当したら新規停止＋通知）
| # | 条件 | 動作 |
|---|---|---|
| ① | 本番開始からのドローダウン 35R | 新規停止（既存はルールどおり決済） |
| ② | 開始から12か月の時点で合計Rマイナス | 新規停止 |
| ②' | 6か月の合計Rが −10R 以下 | 継続。点検の通知（直近30件の初期ストップ率・勝ちの平均を添える） |
| ③ | 実コスト（実スプレッド＋実滑り）が想定の1.5倍超（20件以上で毎月判定） | 新規停止 |
| ④ | 1件の損失が −3R 超 | 新規停止。再開は司令塔判断 |

- 再開は、司令塔の操作（Firestore のフラグ解除。画面のボタンから）でのみ行う。

## 8. 緊急停止
- trading-app-v2 の画面と、Firestore のフラグの両方から止められる。
  - 「新規停止」: 既存はルールどおり
  - 「全決済」: 成行で全決済し、全注文を取り消す
- 停止の操作が**黙って失敗しない**こと（BTC 実行層の欠陥②の教訓）。
  - 実行結果を必ず画面に返す。
  - 失敗したら、次の回で再試行して通知する。

## 9. 安全設計のチェックリスト（BTC 実行層の監査で見つかった欠陥②〜⑨の教訓を含む）
- [ ] 二重発注の防止: clientOrderId を「イベントID＋候補番号」から決めて付与し、同じ ID の注文は出さない
- [ ] 数量の丸め方向（リスクを増やす側に丸めない）
- [ ] 決済数量が建玉数量と一致する（部分約定を含む）
- [ ] ストップの価格が正しい側にある（買いは下、売りは上）。逆なら発注しない
- [ ] 証拠金チェックの符号・単位
- [ ] API エラー・タイムアウト・メンテナンス（ERR-5201/5202）時は新規を出さず、次の回で突き合わせから再開する
- [ ] 時刻はすべて JST に揃え、夏時間の切り替え（GMO の営業日の開始が6時／7時）を考慮する
- [ ] ログに API キー・署名を出さない
