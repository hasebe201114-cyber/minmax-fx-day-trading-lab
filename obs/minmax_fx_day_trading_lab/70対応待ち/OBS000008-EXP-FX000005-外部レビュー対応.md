### F1: 週末強制クローズが一度も発動していない（実装バグ）

```
train       n= 345  週末跨ぎ= 27 ( 7.8%)  WEEKEND_*決済=0
validation  n= 104  週末跨ぎ=  6 ( 5.8%)  WEEKEND_*決済=0
test        n= 173  週末跨ぎ=  8 ( 4.6%)  WEEKEND_*決済=0
合計: 41/622 件（6.6%）が土曜 06:00 JST を跨いで保有
```

原因は `is_weekend_close_time(ts) = (ts.weekday()==5 and ts.hour>=6)` が
**「土曜 06:00 以降の H1 バーの存在」を前提**にしている点。市場が閉まっているためそのバーは
DS-1 に存在せず、条件は一度も真にならない。

典型例（train 1 件目）: USD/JPY、金曜 21:40 エントリー → 月曜 21:00 決済、`SL_INITIAL_NO_TP`、
`r_gross = -1.0`。**週末ギャップを跨いだ挙句、ストップは正確なストップ価格で約定した扱い**になっている。

PJ 共通ルール「週末持ち越し禁止」および `01-trade-scenario-definition.md` §2・§4.7 が、
実装によって保証されていない。→ **T-01**

`src/minmax_fx_dt/backtest/simulator.py:420` の同名ロジックにも同じ欠陥がないか要確認
（SYS-FX007〜010 の過去判定に波及しうる）。

### F2: `permutation_p < 0.05` は 4 通貨構成では原理的に達成不能（検定設計の欠陥）

```
4通貨・全トレード勝ち（理論上ありえない最強のエッジ）を入れた場合:
  n=   100  p=0.3158
  n= 1,000  p=0.3158
  n=20,000  p=0.3158
参考: 単一通貨・全勝 n=100 なら p=0.000050
```

`permutation_test_clustered()` は**通貨ペアごとに符号を 1 個だけ引き、そのペアの全トレードに
一括適用**する。したがって検定の実効標本サイズは「トレード数」ではなく「通貨ペア数 = 4」。
さらに JPY クロス 4 本は平均相関 0.808（実効独立数 1.168）。

**p 値の下限が 0.3158 で、n をいくら増やしても 1 桁も動かない。**
報告されている `p = 0.3866 / 0.4625 / 0.4705` は、戦略の情報をほぼ含んでいない。

`01-trade-scenario-definition.md` §11 課題 4 の記述「帰無分布が離散的（最大 32 通り）で
分解能が粗い」は問題を過小評価している。分解能ではなく**検出力がゼロ**であることが問題。→ **T-06**

本関数は 2026-08-18 追加のため SYS-FX010 以降の判定に効いている。

### F3: ATR トレーリングストップが事実上一度も作動していない

```
決済理由別 r_gross（全期間プール）:
  SL_INITIAL_NO_TP   n=238  中央値 -1.000  min -1.00  max -1.00
  TP_THEN_SL_TRAIL   n=225  中央値 +0.400  min +0.40  max +1.53
  TP_FULL            n=158  中央値 +2.100  min +2.10  max +2.10

TP_THEN_SL_TRAIL 225 件のうち 89.3% が建値ストップの値ちょうど
  （+0.40: 116 件 = TP1 のみ到達 / +1.10: 85 件 = TP1+TP2 到達）
```

`atr_trail_multiplier = 3.23` は SYS-FX009 の**H1 設計**からの転用。本戦略の 1R は
**M5 スケール**（`leverage_ratio = entry_price/initial_risk` の中央値 826 → USD/JPY 150 円なら
1R ≈ 18pips）なので、`3.23 × ATR(H1)` は概ね **3〜4R 相当**。TP3 = 4R の全量利確に先に到達し、
原理的に噛まない。

**`01-trade-scenario-definition.md` §5.3 が記述している出口は、実際には
「段階利確＋建値ストップ」のみ。** 「トレーリングで利を伸ばす」設計は**まだ一度も検証されていない**。
§11 課題 5（ペイオフ 1.0 近辺）の直接原因である可能性が高い。→ **T-02 / T-13**

### K3m（最大連続損失 ≤ 5）はスケール不変でない

```
train       n=345 勝率 63.8%  観測 6  i.i.d.期待値 5.41  「≤5」通過率 59.3%  観測パーセンタイル 0.59

```

**エッジが本物であっても、この基準は約 6 割でしか通らない。** 観測値のパーセンタイルはいずれも
0.28〜0.72 で、ランダムと区別がつかない。改善ループ第 3 試行で「Test の最大連敗が 8→5」を
カレンダーフィルタ採用根拠の一つにしたが、主にノイズを選んでいる（第 4 試行 Part B で 5→6 に
戻ったのも同様）。→ **T-08**

### `min_n_trades = 300` と実効 n 係数の二重計上

```
実効通貨ペア数 = 1.168  縮小係数 = 0.292
→ n_eff = 300 に必要な名目トレード数 = 1,027 件
   train 名目 345（不足 682）/ validation 名目 104（不足 923）/ test 名目 173（不足 854）
```

Test 期間 8.5 ヶ月・4 通貨なら **1 ペアあたり月 30 トレード**。
「週 1 回程度の高ボラを厳選する」という戦略コンセプトと**定義上両立しない**
（`00-prescreen.md` の想定では Train 74 週 × 5 通貨で母数上限 370 件）。

さらに `MIN_N_TRADES_STATISTICAL = 300` 自体が**独立トレード前提**の検出力シミュレーション
（勝率 60%）から出た値。そこへ相関ハンデを重ねると罰則が二重に効く。→ **T-07**
