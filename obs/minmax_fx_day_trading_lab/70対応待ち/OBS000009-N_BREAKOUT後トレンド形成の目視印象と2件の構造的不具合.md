## 1. 目視印象の検証結果

### 1.1 「ブレークするとトレンドが出る」は、対照群と区別できない

アンカー = ブレイク H1 バーの終値（＝バー確定時刻、先読みなし）。
順行 ±1ATR の対称バリアレース（最大 72 H1 バー）で「トレンドが形成されたか」を定義した。

| 群 | n | 順行バリア先着率（決着分） |
|---|---|---|
| **BREAKOUT**（レンジ/ATR ≥ 3.5） | 261 | **49.4%** |
| CTRL_ALL（同期間の全 H1 バーを、そのバー自身の陽線/陰線方向でアンカー） | 7,500 | 49.6% |
| CTRL_NORMAL（レンジ/ATR が 1.0〜1.5 の平凡なバー） | 7,499 | 50.4% |

**大きいバーの後だからといって、普通のバーの後より方向が続くわけではない。** ATR(H1) 中央値は
往復コストの 6.8〜14.6 倍あるため、この結果はコストで潰れているのではなく、単に方向性のエッジがない。

### 1.2 「戻ってからトレンド」も、リークを外すと消える

司令塔の言う「戻り」を、既存の確定済み定義（ブレイクバー確定後 30 分〜3 時間、M15 判定、
`vol_breakout_retrace_window.json`）で測り、ブレイクバーレンジの 50% 以上戻したかで層別した。

| 層 | 判定方法 | 順張り勝率 | 逆張り勝率 | n |
|---|---|---|---|---|
| RETRACED（50%以上戻した） | **リーク版**（ブレイクバー終値起点でレース） | 19.8% | **80.2%** | 118 |
| RETRACED | **リークなし版**（戻り判定窓の終端で建て直してレース） | 50.5% | **49.5%** | 118 |
| NOT_RETRACED | リーク版 | 73.2% | 26.8% | 143 |
| NOT_RETRACED | リークなし版 | 50.0% | 50.0% | 143 |

「リーク版」は、戻り幅を測る窓（ブレイク後 30分〜3時間）と勝敗を測る窓（ブレイクバー終値起点）が
重なっている。ブレイクバーのレンジは定義上 3.5ATR 以上なので、その 50% を戻した時点で逆行 1ATR
バリアにはほぼ必ず触れている。**「大きく戻った群は逆張りが勝つ」は同義反復**であり、実運用では取れない。

戻り判定窓が終わったあとの値動きだけで測り直すと、順張り 50.5% / 逆張り 49.5% で**コインフリップ**に戻る。

### 1.3 司令塔の逆張り仮説への回答

**「戻りでブレーク方向と逆にエントリーすれば勝率が上がる」は、Train データでは支持されない**
（逆張り勝率 49.5%、n=118）。±1ATR の対称バリアなので順張り勝率と逆張り勝率は必ず足して 1 になり、
どちらか一方が有利になることは、順張りに不利なエッジが実在する場合に限られる。それが観測されていない。

ただし本診断は「±1ATR 対称バリア・勝率」という一つの定義での結果であり、
非対称な RR（例: 逆張り 0.5ATR 利確 / 1.5ATR 損切り）や保有期間を変えた場合は未検証。

### 1.4 なぜチャートでは「見える」のか

- **事後選択**: チャートを見る時点で、ブレイク後の値動きが既に描画されている。「戻って伸びた」形は
  目に留まり、「戻って往復しただけ」「戻らず失速した」形は数えられない。
- **サンプル数**: 提示された 2 枚のチャートはいずれも USD/JPY 約 2 週間で 4 シグナル。本 PJ の事前登録
  プロトコルは同じ条件で 5 通貨 17 ヶ月 261 イベントを測っている。
- **MA の後追い**: 大きいバーの後は短期 MA が必ず一方向に開く。これは「トレンドが出た」証拠ではなく、
  MA の定義上の帰結。
- **リーク 1.2 と同型**: 目で「戻り」を確認した瞬間、既にその後の値動きも視野に入っている。

## 2. 不具合1: エントリー探索窓の起点がバーオープン時刻になっている（先読み）

### 事実

- `00-spec.md` §「探索窓 M」および §「エントリー層」は「ブレイクバー**確定後** 30 分」と明記している。
- 実装 `scripts/backtest_vol_breakout_dow_theory.py:345-347` は
  `break_time = h1.index[break_idx]` / `start_time = break_time + 30分`。
- `to_h1()` は `resample("1h")` を label 既定（= left）で使うため、`h1.index[i]` は**バーのオープン時刻**。
  実測で確認済み（`h1.index[i]` の 1 時間分の M5 を集計するとその H1 バーの高安終値に一致）。
- したがって探索開始は「バーオープン + 30 分」＝**バー確定の 30 分前**。この時点では
  レンジ/ATR ≥ 3.5 も、`close > open` による UP/DOWN 判定も、`break_bar["high"]/["low"]`（初期基準値）も
  確定していない。
- 同じ起点の取り方が `analyze_vol_breakout_retrace_window.py`（retrace_ratio = 0.55 の導出元）にもある。
  そちらは docstring に「バーオープン時ではない」と明記しながら実装が一致していない。

### 影響量（実測）

凍結最良候補（T-13 トレール専業版）の全トレードを、生成元ブレイクイベントに紐づけ直して計測した。
トレード数は公式 ledger と完全一致（Train 524 / Validation 133 / Test 170）。

| 期間 | 全トレード | うちバー確定前（オフセット < 60分）のエントリー | 比率 | オフセット中央値 |
|---|---|---|---|---|
| Train | 524 | 41 | 7.8% | 40 分 |
| Validation | 133 | 17 | 12.8% | 40 分 |
| Test | 170 | 20 | 11.8% | 40 分 |
| 合計 | 827 | **78** | **9.4%** | 40 分 |

平均 r_gross は Train +0.66 / Validation −0.04 / Test +1.70（該当外はそれぞれ +0.58 / +0.72 / +0.51）で、
一方向に成績を押し上げているわけではない。ただし**実運用では執行不可能なエントリーが 1 割弱含まれている**。

### 想定される対応（司令塔判断待ち）

1. `start_time = h1.index[break_idx] + 1h + 30分` に修正（spec の文言どおり）し、TVT を再実行する。
2. あわせて retrace_ratio の導出（`vol_breakout_retrace_window.json`）も同じ起点で測り直す。
3. 「起点をバーオープンにする」を仕様として採用するなら、シグナルをリアルタイムで判定可能な形
   （バー途中のレンジのみで判定、方向は確定前の値で決める等）に検出層ごと再定義する必要がある。

## 3. 不具合2: SYS-FX012 フォワードテストがデータを蓄積していない

### 事実

- `research/method-notes/sysfx012_forward_test_ledger.json`（generated_at 2026-08-25T23:36Z ＝ 08-26 08:36 JST）は
  `n_events_raw: 0` / `n_trades_total: 0` を記録している。
- しかし本リポジトリの `data/raw/ds-1-forward/*.csv` には、cutoff（2026-08-15 06:00 JST）以降に
  **3 件の N_BREAKOUT イベント**が存在する:

  | 通貨 | 時刻(JST) | レンジ/ATR | 方向 |
  |---|---|---|---|
  | USD/JPY | 2026-08-19 21:00 | 5.00 | DOWN |
  | EUR/JPY | 2026-08-19 21:00 | 4.43 | DOWN |
  | GBP/JPY | 2026-08-19 21:00 | 4.31 | DOWN |

- 生 CSV から `data/curated/ds-1.json` / `ds-1-forward.json` 相当を復元して
  `run_forward_test_cycle.run_forward_cycle()` をそのまま実行すると
  **`n_events_raw: 3` / `n_events_dedup: 3` / `n_events_trendfiltered: 2`** を返す（トレードは 0 件のまま）。
  つまりコードは正しく、**入力データが欠けている**。

### 原因

- `data/curated/ds-1-forward.json` は `.gitignore:72` で追跡対象外。
- `.github/workflows/update-ds1-forward.yml` は毎時、**新規チェックアウトのランナー上で**
  `fetch_m5_ohlcv.py --lookback-days 2` を実行し、「既存ファイルに追記マージ」する設計だが、
  ランナーは毎回まっさらなので**追記先の既存ファイルが常に存在しない**。commit もしない
  （ワークフロー自身のコメントに「1.4MB+ の更新で履歴が膨らむのを回避」と明記）。
- 週次の `sysfx012-fx-forward-cycle.yml` も同様に、`ds-1.json` を生 CSV から再生成したうえで
  `--lookback-days 2` を叩くだけ。
- 結果としてフォワードテストが見られるデータは
  **[warmup: 〜2026-08-15 05:55] + [直近 2 日]** で、その間が丸ごと欠落する。
  `latest_bar_by_pair` が最新（08-26 08:35）に見えるため、外形上は正常稼働に見える。

### 帰結

- **2026-08-15 のフォワードテスト開始以降、実質的に何も蓄積されていない。**
  ledger の `n_events_raw: 0` は「相場が静かだった」ではなく「データに穴がある」。
- 30/60/90 日チェックポイント（2026-09-14 / 10-14 / 11-13）は、このままでは成立しない。
- PJ000003 の「GitHub Actions 3 ワークフローすべての継続稼働を確認済み」（2026-08-26）は、
  プロセスが動いていることの確認であって、データが蓄積されていることの確認ではなかった。

### 想定される対応（司令塔判断待ち）

1. `ds-1-forward.json` を、`ds-1.json` と同じく**生 CSV（`data/raw/ds-1-forward/*.csv`）から再生成**する方式に変える。
   生 CSV は 100MB 制限に収まり git 管理できるため、ランナー間で永続化される。
   `fetch_m5_ohlcv.py` に CSV 出力を追加し、毎時ワークフローで CSV を commit する。
2. または `ds-1-forward.json` 自体を commit 対象にする（サイズ増と引き換えに最小変更）。
3. どちらにせよ、**ledger に「cutoff 以降のデータ被覆率」を出力**し、穴が空いたら気づけるようにする。
   （今回、`n_events_raw: 0` と「静かな相場」が区別できなかったのが本質的な問題）
4. 2026-08-15〜08-24 の生 CSV は既に手動 commit 済みなので、その範囲は復元可能。
   08-24 以降は GMO API の保持期間内であれば再取得できる。

### 不具合2 対応（2026-08-27、司令塔承認のうえ着手・完了）

上記「想定される対応」1・3・4 を実施した。2 の「ds-1-forward.json 自体を commit 対象にする」は
採らなかった（CSV の方が ds-1 と一貫した形式で、差分も小さく履歴が肥大化しにくいため）。

1. **`load_m5_forward()`（`scripts/forward_test/run_forward_test_cycle.py`）を修正**し、
   `data/curated/ds-1-forward.json`（.gitignore対象・非永続）ではなく
   `data/raw/ds-1-forward/*.csv`（git管理・永続）を正の情報源にした。
   `ds-1-forward.json` は同一実行内で直前に取得した最新データを追加で重ねる
   補助的な役割に格下げ（存在しなくても動く）。
2. **`fetch_m5_ohlcv.py` を書き直し**、GMO API から取得したデータを
   `data/raw/ds-1-forward/ohlcv_{pair}_5min_live.csv`（1通貨1本の追記型CSV、
   `scripts/data/fetch_ds1_ohlcv.py` と同じスキーマ）に永続化するようにした
   （既存の手動コミット分ファイルとは別ファイルとして共存、`load_m5_forward()` 側は
   `ohlcv_{pair}_5min_*.csv` の glob で両方を透過的に結合する）。
3. **`update-ds1-forward.yml`（毎時）に commit/push ステップを追加**し、
   `permissions: contents: write` に変更（従来は `read` のみで意図的に commit しない設計だった）。
4. **`sysfx012-fx-forward-cycle.yml`（週次）にも同じ commit ステップを追加**（毎時ジョブが
   何らかの理由で失敗していた場合の冗長経路）。
5. **`compute_data_coverage()` を新設**し、ledger 出力に `data_coverage`
   （通貨別の cutoff 以降バー数・最大ギャップ・`has_gap` フラグ）を追加。
   `n_events_raw: 0` が「相場が静か」か「データの穴」かを次回から区別できるようにした
   （週末クローズ最大60時間は正常として扱い、それを超えるギャップのみ `has_gap: true`）。
6. **実際に GMO 公開 API から 2026-08-23〜08-27 分（4通貨×1,048本=4,192本）を取得し、
   `data/raw/ds-1-forward/*_live.csv` として commit 済み**。これで cutoff（08-15）以降の
   データは [08-17 07:00〜08-22 05:55]（手動分）+ [08-22〜08-24]（手動分）+
   [08-23〜08-27 22:15]（今回自動取得、重複は dedup 済み）で連続する
   （08-15 06:00〜08-17 07:00 は土日クローズで元々データが存在しない期間、`has_gap: false` で正常判定）。
7. **`run_forward_test_cycle.py` を実行して ledger を再計算**した結果、
   `n_events_raw: 0 → 3`（`n_events_dedup: 3`・`n_events_trendfiltered: 2`）に変わった。
   ただしトレード数は 0 のまま（2件の候補イベントいずれも、凍結済みダウ理論エントリーロジックの
   構造上プルバック確認が成立せずエントリーに至らなかった可能性が高いが、これは
   `simulate_dow_theory_trend()` 自体の凍結済み仕様であり、本対応のスコープ外のため未調査）。
8. `PYTHONPATH=src python3 -m pytest tests/ -q` で既存回帰テスト99件全件passを確認（本修正が
   触れたのはフォワードテスト専用のライブ取得・読み込み経路のみで、凍結済みTrain/Validation/Test
   バックテストエンジンには一切触れていない）。

**未対応（別スコープ）**: 不具合1（エントリー探索窓の先読み）は本対応に含めない。司令塔判断待ちのまま。
