## 内容
`scripts/backtest_vol_breakout_dow_theory.py` の `simulate_dow_theory_trend()` は、5分足 i（開始時刻 ts）を処理するときに次のように判定している。

```python
cur_h1_pos = int(confirm.index.searchsorted(ts, side="right") - 1)
...
h1_high_hp = float(confirm["high"].iloc[hp])   # hp は cur_h1_pos まで
confirmed = awaiting_h1_confirm and h1_high_hp > h1_confirm_threshold
```

- `confirm`（既定は h1）は `resample("1h")` の左端ラベル。`cur_h1_pos` は ts を含む、**まだ形成途中の H1 足**を指す。
- その足の high/low は、その時間の残りの5分足（未来）を含む。例: 10:05 の5分足の時点で、10:00〜10:59 の高値を使っている。
- これにより、型崩れ後の「H1 継続確認による再開」が、**その時間のうちに高値更新が起きることを知った状態で**行われる。
  - 現行 Train の約7割の取引は、この再開に由来する（関数の docstring の診断記載）。
- 同様に、急変フィルター（`price_shock_filter.make_price_shock_check`）も、形成途中の H1 足の値幅で抑制を判定している。

### 1. 先読みの所在（コード読解）
- `simulate_dow_theory_trend()`（401〜430行）は、5分足 i（開始 ts、判定は確定時 ts+5分）を処理するとき、`confirm.index.searchsorted(ts, side="right") - 1` で **ts を含む H1 足**を取り、その `high/low` を読む。`to_h1()` は `resample("1h")` の左端ラベルなので、この足は HH:00〜HH:59 の全体（最大55分先の5分足を含む）である。
- しかもこの読み込みは**その時間の最初の5分足（HH:00）で1回だけ**行われる。つまり HH:00 の時点で「この1時間に高値更新が起きるか」を知った状態で再開し、`running_extreme` を HH:00 の足の高値に置いて押し目探索を始める。
- `h1_extreme_since_break`（再開の閾値）も、形成途中の H1 足全体で更新される（仕様は「M5 型崩れ時点までの H1 高値」）。
- 急変フィルター `price_shock_filter.make_price_shock_check()`（98〜102行）も、ts を含む H1 足の値幅（その時間の終わりまで）で抑制を判定する。

### 2. 具体例（USD/JPY、2024-03-19 12:00 のブレイク、UP）
| 時刻（JST） | 公式 | 実時間版（running） |
|---|---|---|
| 2024-03-20 夜 | 22:10 に M5 で型崩れ → 待機。閾値 151.820 | 23:00 に M5 で型崩れ → 待機。閾値 151.820（同じ値） |
| 2024-03-22 10:00 | **再開**（10:00 の H1 足の高値 151.866 を参照。この高値は 10:50 の5分足で付く＝50分後） | 待機中（10:00 の5分足の高値は 151.580） |
| 10:05 確定 | **エントリー 151.505**（押し目 151.493） | 待機中 |
| 10:35 確定 | — | 5分足の高値 151.845 が閾値を超え、ここで再開 |
| 10:40 確定 | — | エントリー 151.800 |
| 結果 | 10:55 決済 **+5.6R**（グロス） | 11:20 決済 **−1.0R** |

公式は、10:05 の時点ではまだ起きていない 10:35〜10:50 の上昇を知って買っている。

### 3. 打ち切りテスト（実装に依存しない確認、`review_c_truncation_test.py`）
公式の各取引について、全4通貨の5分足を**エントリー足の確定時刻で打ち切り**、H1・ATR・急変フィルターを打ち切り後のデータから作り直して、公式関数を同じブレイクイベントで再実行した。因果的な計算なら 100% 同じエントリーが再現するはずである。

| 期間 | 公式件数 | 再現しない件数（うち再開由来） | 再現しない取引の合計R・勝率 | 再現する取引の合計R |
|---|---|---|---|---|
| Train | 308 | **112**（111） | **+94.0R**・78.6% | +5.2R |
| Validation | 83 | **30**（30） | **+42.5R**・93.3% | +3.8R |

- 原因は全て継続確認側。急変フィルターだけ打ち切った場合に再現しない取引は0件（急変フィルターの先読みは、公式の取引を作るのではなく、抑制する側にだけ効いている）。
- 再現しない取引のエントリー時刻は、毎時 05〜20分に集中（Train 112件中 108件）。これは「HH:00 に1時間分を見て再開する」実装の特徴そのもの。
- 公式の「再開由来」取引（Train 205件）は、毎時 00〜25分のエントリーが 180件 +104.7R、30〜55分が 25件 −5.6R。実時間版では分布が均一になり、合計もほぼゼロになる。
- 注: このテストはエントリー**以後**のデータへの依存しか検出しない。それより前の時間で先読みした結果として経路が変わった分は、下の再実装で測る。

### 4. オーケストレーターの修正版の点検
- **+55分ずらし（確定済み H1 足のみ）**: 境界は正しい。H1 足 HH は、HH:55 開始の5分足（確定 HH+1:00）の処理から見える。初期化（`last_h1_pos_checked` がブレイク足の1本前になり、最初の処理でブレイク足を読み直す）も結果に影響しない。データの欠けがあっても先読みにはならない。
- **confirm_bars=m5（実時間版）**: 初期化（ブレイク足の5分足〜追跡開始までの高値を閾値に入れる）、`h1_extreme_since_break` の扱い、再開時の `running_extreme`（再開した5分足の高値）、いずれも因果的で正しい。H1 の「形成途中の足のその時点までの高値」で判定する版と数学的に同じになる。
- **軽微な指摘（確定済み H1 足版）**: 閾値が確定足だけで作られるため、型崩れ**前**に同じ時間内で付けた高値によって、その時間の終わりに「再開」してしまうことがある（仕様は「型崩れ以降の H1 高値が、型崩れ時点までの高値を更新したら」）。閾値に形成途中の H1 足のその時点までの高値を入れた版（closed_strict）では件数が減るが、結論は変わらない（下表）。
- オーケストレーターの表に無い組み合わせ「継続確認・急変フィルターとも確定済み」は 265件 +10.5R / 68件 −15.8R（実測で再現）。

### 5. 独立再実装の数値（`review_c_causal_reimpl.py`）
オーケストレーターのモンキーパッチとは別に、追跡ロジックを書き直した（DOWN は価格を符号反転して UP 形式で追跡し、決済は公式関数）。公式モードで **308件 +99.22R / 83件 +46.26R を完全再現**し、オーケストレーターの各版の数値（288/−20.68、275/−30.02、278/+13.60 など）も一致した。

| 継続確認 | 急変フィルター | Train 件数 / 合計R / p | Validation 件数 / 合計R / p | 合算 平均R [95%CI]（日単位ブートストラップ） / p |
|---|---|---|---|---|
| 公式（先読み） | 公式（先読み） | 308 / +99.2R / 0.055 | 83 / +46.3R / 0.092 | +0.372 [+0.187, +0.553] / 0.024 |
| 実時間 | 公式（先読み） | 288 / −20.7R / 0.61 | 77 / +4.6R / 0.43 | −0.044 [−0.198, +0.119] / 0.60 |
| **実時間** | **確定済み** | **278 / +13.6R / 0.40** | **76 / +8.1R / 0.38** | **+0.061 [−0.192, +0.408] / 0.41** |
| **実時間** | **実時間（形成途中の値幅で発動）** | **278 / +15.3R / 0.41** | **76 / +8.1R / 0.38** | **+0.066 [−0.177, +0.411] / 0.38** |
| 確定済み | 確定済み | 265 / +10.5R / 0.43 | 68 / −15.8R / 0.74 | −0.016 [−0.259, +0.359] / 0.53 |
| 確定済み（厳密） | 確定済み | 251 / +6.7R / 0.45 | 66 / −18.7R / 0.79 | −0.038 [−0.291, +0.341] / 0.57 |

- p は公式と同じ日単位ブロックの permutation（符号反転、seed=42）。
- 実時間版の中央値は −0.25R、勝率 43.5%（公式は中央値 +0.39R、勝率 61.4%）。
- 実時間版のプラスは USD/JPY 2024-05-02 05:00 エントリーの 1件（+46.1R）に依存する。除くと Train+Val 合算で −22.7R（急変フィルター実時間）/ −24.4R（確定済み）。

**実運用で再現できる「正しい」定義**: 継続確認は「実時間」版（各5分足の確定時点の、形成途中の H1 足のその時点までの高値・安値で判定）が、仕様の文言に最も忠実で、かつ実装可能。急変フィルターは「確定済み」でも「実時間」でも実装できる（数値はほぼ同じ）。どの定義を選んでも優位性は無いため、定義の選び方は判定を変えない。

### 9. 推奨
1. SYS-FX012 の本番移行（OBS000014/017）を止める（司令塔判断）。実行層は T0（移植）で凍結。
2. `simulate_dow_theory_trend` の継続確認と急変フィルターを因果的な定義に直す（既定を実時間版に）。あわせて「エントリーはエントリー以後のデータに依存しない」ことを確かめる打ち切りテストを、全戦略の回帰テストとして常設する。
3. 今回の結果を見たうえで Train/Validation でパラメータを調整し直して優位性を取り戻そうとしない（データスヌーピングになる）。新しい設計は新しい EXP として spec を先に固定し、Test は未使用のまま残す。

5. portfolio-ledger と PJ 系の進捗サマリに、本件を「負の結果」（先読み由来の偽陽性）として記録する。
