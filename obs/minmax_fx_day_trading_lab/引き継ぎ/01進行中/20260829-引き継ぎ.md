## 発見したバグ（本セッションの中心）

### フォワードデータ消失バグ

**症状**: `sysfx012_forward_test_ledger.json`が`n_events_raw: 0`（cutoff以降イベントゼロ）を報告し続けていた。

**原因**: `data/curated/ds-1-forward.json`を.gitignore対象にした一方で、毎時workflow `update-ds1-forward.yml`は「既存JSONへ追記マージ」した結果を**何もコミットしていなかった**（`permissions: contents: read`、commitステップ無し）。GitHub Actions runnerは毎回使い捨てのため、追記結果はジョブ終了とともに消える。週次cycleがフォワード区間として読めるのは常に「実行直前の`--lookback-days 2`分」だけで、cutoff（2026-08-15 06:00 JST）以降の大半が恒久的な空白だった。

**混入経路**: 既存の`scripts/forward_test/weekly_cycle.py`は元々「`data/raw/ds-1-forward/`にCSVを保存 → `aggregate_to_json()`でJSONを生成」という正しい構造で書かれていた。2026-08-26に追加した2つのworkflowだけがこの正本を迂回し、JSONだけを直接触っていた。

**真値**: バックフィルして再計算した結果、イベントは**6件**だった（0件ではない）。

**なぜ2週間気づかれなかったか**: ledgerは「イベントが無かった」のか「データが無かった」のかを区別できる情報を持たない。`latest_bar_by_pair`は毎回2日分の取得で更新されるため正常に見えた。2026-08-24に発覚したClaude Routineの不具合（成功と記録されるのに実データが更新されない）と同型の"無音の失敗"であり、**「ワークフローが成功しているか」ではなく「実データが増えているか」で確認すべきだった**という教訓は前回と同じ。

**修正**:

1. バーの正本をgit管理の追記型CSV `data/raw/ds-1-forward/*_forward.csv` に移し、`ds-1-forward.json`はそこから再生成できる派生物として扱う（`data/raw/ds-1/`＋`ds-1.json`と同じ構造に統一）
2. `fetch_m5_ohlcv.py`: `load_forward_csv`/`write_forward_csv`/`pair_dict_from_records`を追加。`load_existing()`はJSONとCSVの和集合を返すため、どちらか一方しか無い環境でも欠落しない。CSVの書式は`scripts/data/fetch_ds1_ohlcv.py`の出力と揃えたので、同ディレクトリの日付範囲別CSVと混在しても`aggregate_to_json()`が結合・重複排除できる
3. `run_forward_test_cycle.py`: `load_m5_forward()`が正本CSVを直接読む（fetchステップの実行順序に依存しない）
4. `update-ds1-forward.yml`: `permissions: contents: write`＋毎時CSVのcommit/push
5. `sysfx012-fx-forward-cycle.yml`: lookbackを2日→**9日**に拡大（週次7日＋余裕2日）。毎時workflowが数日止まっても週次で穴が自動的に埋まる（self-healing）。ledgerと同時にCSVもcommit

## 重要な懸案（次セッションが引っかかりやすい点）

### 1.（解決済み）修正をmainへマージし、CI上で動作を確認済み

司令塔指示によりコミット`2088498`を`main`へfast-forwardマージ・push済み（2026-08-29）。`update-ds1-forward.yml`を`main`で手動起動して検証した結果（run 33242580649、success）:

```
  USD_JPY  n_bars= 2856 end=2026-08-29T05:55:00+09:00
  EUR_JPY  n_bars= 2856 end=2026-08-29T05:55:00+09:00
  GBP_JPY  n_bars= 2856 end=2026-08-29T05:55:00+09:00
  AUD_JPY  n_bars= 2856 end=2026-08-29T05:55:00+09:00
  追加: 0 bars (4 通貨合計) / 変更なし、コミットをスキップ
```

**使い捨てrunner上で`ds-1-forward.json`が存在しないにもかかわらず、コミット済みCSVからフォワード全期間（2,856本／通貨）が復元されている**ことが確認できた。修正前の同じステップは常に約576本（2日分）しか持てなかった。この実行でコミットが発生しなかったのは土曜（FX市場休止）で新規バーが0本だったためで、ログに`追加: 0 bars`と明示されているので「データが無い」と「壊れている」を区別できる。

次セッションでは`git log --oneline -5 -- data/raw/ds-1-forward/`で、平日に毎時コミットが積まれているかを確認すること。

なお、消失していたのは「M5 OHLCV」であって「ライブ気配値（bid/ask）」ではない。`live-ticker-poll.yml`は正しく`data/raw/live-ticker/`をコミットしており、こちらは無事（2026-08-24〜29で54回分・216行）。

### 2. フォワードテストのトレードが0件（設計どおりだが、判断が必要になりうる）

修正後の第1〜2週（10営業日・4通貨）の内訳:

| 除外理由 | 件数 |
|---|---|
| H1ダウ理論トレンド判定不能 | 3 |
| 価格反応型ショック抑制フィルター（複数通貨同時ブレイク） | 3 |
| M5エントリー成立 | 0 |

検出された6件は2つの時刻クラスタ（2026-08-19 21:00・08-28 23:00）に集中し、いずれも複数通貨が同時にブレイクした局面だった。改善ループ第7試行で導入した同フィルターはまさにこのパターンを抑制する設計なので、**バグではない**。ただしこの頻度が続くと30/60/90日チェックポイント（2026-09-14 / 10-14 / 11-13）に評価対象トレードがほぼ無い状態で到達する。10営業日・6件では傾向とは言えないため、**設計変更はしていない**（HARKing防止プロトコル上、設計変更は事前登録のやり直しを要する）。次のチェックポイントで同傾向が続くなら司令塔判断（設計変更の事前登録をやり直すか、フォワードテストを打ち切るか）が必要。

### 3. 毎時ワークフローの実行率が想定より低い

`live-ticker-poll.yml`は毎時cron（`5 * * * *`）だが、2026-08-24 01:09〜08-29 02:06の約121時間で記録は54回分しかない（実行率およそ45%）。GitHub Actionsのスケジュール実行は遅延・スキップされることがある既知の挙動で、致命的ではないが、**「毎時記録される」前提でスプレッド時系列（DS-2）の代表性を語る際は注意が必要**。週次cycleのlookbackを9日に広げたのは、この実行率でも穴が埋まるようにするため。

### 4. 市場休止中のティックも記録されている

週末（`market_status=CLOSE`）のスナップショットではスプレッドが8〜14 pipsに開いた値が記録されている（例: 2026-08-29 GBP/JPY 14.2 pips）。`reconcile_divergence.py`側の扱いは未確認。DS-2としてスプレッド代表値を導出する際は`market_status=OPEN`で絞る必要がある（Stage 1受け入れ基準Cの「市場休止中の誤検出チェック」に相当）。
