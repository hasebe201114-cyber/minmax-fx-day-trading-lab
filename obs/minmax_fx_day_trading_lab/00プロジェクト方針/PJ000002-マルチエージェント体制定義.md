# PJ000002 - マルチエージェント体制定義（minmax-fx-day-trading-lab）

> 担当: 司令塔（ユーザー）+ S 戦略チーム
> lp-strategy-lab で確立した 6体マルチエージェント体制を FX デイトレード版へ適用する

## 体制

FX デイトレード検証の進め方は、**ユーザー（司令塔）+ 6体のマルチエージェントチーム**で行う。
lp-strategy-lab で確立した定義（obs/lp_strategy_lab/00プロジェクト方針/PJ000002）と同じ構造・役割分担を踏襲する。
ティア構成: S・C = opus、A・B・D = sonnet、E = haiku（エイリアス指定で常に最新定義に自動追従）

## エージェント一覧

各エージェントは `.claude/agents/*.md` に定義を置く。

### S 戦略チーム (chief-strategist)
- デイトレードFX市場の大局観・**戦略カテゴリ間の期待値/優先順位付け**・全体監視・司令塔への具申
- 市場レジーム（トレンド/レンジ/高ボラ）と戦略の相性分析
- 採用判定のドラフト（最終GOは司令塔）

### A 設計チーム (strategy-architect)
- 検証仕様（spec）確定
- **評価基準（K1d〜K6d）を試算前に数値で固定**
- 通貨ペア・足種・パラメータ空間の設計

### B 実装チーム (quant-researcher)
- spec に忠実な実装
- Tick/分足レベル + ブローカーAPI 連携の**生データのみ**出力（評価はしない）
- HARKing 防止: 結果を見てから仕様を変えることを禁止

### C 品質チーム (adversarial-reviewer)
- 良好結果を疑い倒す、楽観バイアスの最終砦
- 採用/不採用の断固たる判定
- LP ラボの C 判定書と同等の品質（24-point review checklist 等）

### D デプロイチーム (integration-deploy)
- 採用後の実行基盤（trading-app-v2 の FX モジュール、または本PJ内 execution モジュール）への組み込み
- 司令塔の明示GO が出るまで起動しない

### E 進行チーム (archivist-pm)
- OBS 移動・引き継ぎ更新・ACTIVE 更新・採用台帳管理
- 週次サマリ PJ000003 の更新

## ワークフロー

```
S (戦略判断・優先順位)
  ↓
A (spec 確定・基準固定)
  ↓
B (実装・生データ出力)
  ↓
C (adversarial review・採否判定)
  ↓
S (司令塔へ具申)
  ↓
司令塔 GO
  ↓
D (実行環境統合)
  ↓
E (台帳・OBS 更新)
```

## 重要な運用ルール

1. **B (実装) と C (品質) は必ず別エージェント**: 同じ実装者が自分の結果を評価しない構造を厳守
2. **採用ゲートは人間**: C の「採用可」は参考意見であり、本番判定（D の起動）は**司令塔の明示GO**を必須とする
3. **不採用結果も変更履歴に残す**（楽観の反対側のナレッジ）
4. **並列実行は OK**: 複数戦略の検証は独立なので並列で進めてよい
5. **Mavis 環境での制約**: lp-strategy-lab での PJ000006 と同等の制約あり
   - 6体マルチエージェントの物理的実行は不可（単一LLM・単一コンテキスト）
   - opus/sonnet/haiku のティア差を完全再現不可
   - `scripts/exp/*` の長時間実行は限定的
   - 強み: 叩き台作成・並列実行（`team` スキル）・ファイル操作は高速、Web検索・リアルタイム情報取得
   - 役割分担: 叩き台は Mavis、本番品質は claude code 環境（opus/sonnet）

## 司令塔への必須エスカレーション 2 点のみ

- S からテーマを受けるとき
- C の判定に対し本番判定の GO が出るとき

それ以外は進行中（ACTIVE.md / STRATEGY-BRIEF.md の 2点参照で自己解決する）。
