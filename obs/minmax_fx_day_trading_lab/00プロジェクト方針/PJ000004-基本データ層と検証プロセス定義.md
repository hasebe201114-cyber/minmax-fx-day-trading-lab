# PJ000004 - 基本データ層と検証プロセス定義（minmax-fx-day-trading-lab）

> 担当: A 設計チーム（spec 確定）+ S 戦略チーム（プロセス監督）
> lp-strategy-lab の PJ000004 相当のドキュメント。本PJ固有の品質ゲート Q1〜Q8 とデータ層を定義する

## 1. 背景

LP 戦略ラボでは「データの壁」（DS-1〜DS-6 の精度不足が複数実験の判定を覆した事例）から、検証プロセス自体を再設計する PJ000004 を実施した。FX デイトレードでも同等のリスクがあるため、**プロジェクト起票と同時に**データ層と品質ゲートを明文化する。

## 2. データ層（DS-FX シリーズ）

| ID | 名称 | 主ソース | 検証粒度 | 必須度 |
|---|---|---|---|---|
| **DS-1** | 通貨ペア × 足種 × 期間の OHLCV | dukascopy / histdata.com / GMO API | 3年 / 1分足以上 | 必須 |
| **DS-2** | スプレッド時系列（ティック or 1分粒度） | GMO 実測 | 6ヶ月 / 1分粒度 | 必須 |
| **DS-3** | 経済指標カレンダー + 発表時刻周辺挙動 | investing.com / ForexFactory | 3年 / イベント単位 | 必須 |
| **DS-4** | セッション境界時刻 + 典型ボラ/出来高 | 自前集計（DS-1 から派生） | 3年 / 1時間粒度 | 必須 |
| **DS-5** | スリッページ代表性データ | GMO テストネット or 0.5 pip 固定フォールバック | 100注文以上 | 必須 |
| **DS-6** | GMO コイン API 仕様 | GMO 公式ドキュメント | n/a | 必須 |
| DS-7 | （将来）代替ブローカー仕様（OANDA / IBKR） | 公式 | n/a | 将来 |

## 3. 品質ゲート Q1〜Q8

### Q1: データ欠損の網羅的検出
- 1分足について全カレンダー日から**価格パスの欠損**を検出
- 経済指標発表時刻の周辺 ±30 分に欠損があれば警告
- 週末/祝日の正常な欠損は除外

### Q2: ウォームアップ期間の前倒し
- 移動平均/RSI 等のインディケータは計算に N 期間必要
- **検証区間の最初の N 期間は必ずウォームアップ**として結果から除外
- ウォームアップを除外しない実装は差し戻し

### Q3: 平滑化系列の併記
- 生の OHLC に加え、ATR/ADX/標準ボラ等の平滑化系列を併記
- 単一指標のみの K ゲートは不可

### Q4: implied コスト（スプレッド + スリッページ）の自動反映
- バックテストは**成行で約定したと仮定 + スプレッド + 0.5 pip スリッページ**を毎回課す
- `params.json` で cost_pips_per_side = 0.5 を明示
- cost_pips_per_side = 0 は差し戻し

### Q5: データソース/取得日の記録
- `data/curated/*.json` の各ファイルに `source` / `fetchedAt` を必須記載
- `data/MANIFEST.json` で全データ系列を一元管理

### Q6: 通貨ペア単位の decimals 整合性
- USD/JPY は 0.001、EUR/USD は 0.00001 等、JPY 系と非 JPY 系で桁数が異なる
- ロットサイズ・P/L 計算時の桁数誤差を CI で検出

### Q7: 当日クロースの保証（デイトレード固有）
- 検証区間内のすべてのトレードは**必ず日本時間でその日の 06:00 までに手仕舞い**（または対応するセッションクローズ時刻）
- それ以降にクローズされたトレードが含まれていれば差し戻し
- 週末持ち越しは**原則禁止**

**2026-08-28 改定（司令塔判断「緩和しても良い。リスク対策は必要」）**: 「絶対禁止」から
「原則禁止＋個別許可制」に改める。戦略の構造上どうしても週末持ち越しが必要な場合に限り、
**司令塔の明示判断**と、以下4点のリスク対策の実装を**必須条件**として個別に許可する
（`research/EXP-FX000018/00-spec-amendment-01.md` §3 が初適用例・実装参照）:

1. **窓開け（ギャップ）約定モデル**: 逆指値・指値が窓開けで飛び越えられた場合、
   トリガー価格ではなく**寄り値で約定**させる。これを実装せずに持ち越しを許可すると
   損失が体系的に過小評価される（Q11 と同種の楽観バイアス）
2. **週末エクスポージャー上限**: 週明け相対窓開けの99パーセンタイル（通貨別・Train実測）を
   使い、想定窓開け損失が MTM equity の一定%（既定10%、K2m 月間DD上限と同水準）を超えないよう、
   週内最終バーで含み損の大きいポジションから削減する
3. **最大保有期間**: 週末フラットが無くなると含み損を無期限に抱えられてしまうため、
   別途の保有上限を設ける（本PJのスコープ「数日〜数週間」に収まる範囲で事前登録する）
4. **証拠金維持率によるロスカット**: 有効証拠金（MTM equity）÷必要証拠金×100 が
   100%未満で全ポジション強制決済、125%未満で新規エントリー停止（GMOコイン外国為替FXの
   実際のルール。EXP-FX000005 T-12 で確認済み）。`equity ≤ 0` のみの破産ガードでは
   生存バイアスが入る

**許可は戦略単位であり、PJ全体の既定は引き続き週末フラットとする。** 既にフォワードテスト等が
進行している戦略の前提を遡って変更してはならない。

### Q8: ブローカー仕様の整合性（デイトレード固有）
- 通貨ペアの取扱状況が GMO コイン 21 ペアに含まれているか
- 取引単位（最小/最大ロット）、スプレッド、レバレッジ、API rate limit が spec と一致するか
- API 仕様変更時の追跡可能性（`data/curated/ds-6-api-spec.json` の fetchedAt）

### Q9: 最大DD（ドローダウン）の定義（全SYS共通、恒久ルール）

**2026-08-21新設（EXP-FX000005外部レビューT-10対応）**。ポジションサイジング方式によって、
最大DDを「初期資金比」「ピーク（直近最大残高）比」のどちらで評価すべきかが異なる。
**この選択は結果を見る前に固定すること**（結果を見た後に変更した場合は`00-spec.md`に
理由・日付・影響を受ける過去の判定を明記すること）。

| サイジング方式 | DD定義 | 理由 |
|---|---|---|
| 固定ロット（残高に依存せず一定通貨量） | **初期資金比** | 複利で残高が変動しても1トレードのリスク量は変わらないため、初期資金を基準にした比率がそのまま実質的なリスク量を表す |
| 複利（残高の一定%をリスクに充てる） | **ピーク比**（直近の最大残高からの下落率） | リスク量自体が残高に比例して変動するため、初期資金比で評価すると、複利で資産が大きく増えた後の変動を実態より過大に見せてしまう（絶対額としては同じ下落でも、初期資金比では常に大きな%になる） |

**過去システムへの適用可否（2026-08-21確認）**: SYS-FX007（`src/minmax_fx_dt/backtest/simulator.py`の`lot_size`固定）・SYS-FX008・SYS-FX009（同エンジン踏襲）・SYS-FX010（`backtest_carry_no_stop_tvt.py`「固定ロット(1lot=1000通貨)」明記）は**いずれも固定ロット方式**であり、初期資金比のDD定義は当時から正しかった。**遡及的な再評価は不要。** SYS-FX011（EXP-FX000005）のみ`risk_pct_per_trade`（残高の1%）による複利サイジングを採用しており、ピーク比DDへの切り替えが必要だった（`01-trade-scenario-definition.md`§6、`evaluate_vol_breakout_dow_theory_kpi.py`の`peak_relative_max_dd_pct()`/`peak_relative_monthly_max_dd_pct()`、および`src/minmax_fx_dt/backtest/metrics.py`の同名関数を参照）。

### Q10: 改善ループの停止条件（全SYS共通、恒久ルール）

**2026-08-21新設（EXP-FX000005外部レビューT-19対応）**。SYS-FX008には「3試行で停止」という上限があった一方、SYS-FX011は明確な上限なしに改善ループが第7試行まで進み、そのたびに「司令塔判断待ち」で止まる運用になっていた。これは「ユーザのオペレーションは最低限に」という開発方針と整合しないため、**Phase 2（prescreen）起票時に上限回数を事前登録する**ことを恒久ルールとする。

- **既定上限**: 改善ループ**5回**（結果を見て採否/設計変更を決めた試行のみをカウント。カウント方法はT-18の試行数え方に準拠し、既知のバグ修正・検定手法自体の是正・外部レビュー対応の修正はループ回数にカウントしない）
- 起票時にSYSTEMS.mdの戦略複雑度に応じて上限を調整してよいが、**結果を見る前に**`00-prescreen.md`または`00-spec.md`に明記すること
- **上限に達し、かつ必須KPIゲート（K1m〜K7m相当）が未達のままの場合、自動的にREJECT（不採用）確定とする**。追加の試行を行いたい場合は新規EXP番号を起票し、そこで新たにループ回数をゼロから起算する
- 上限到達前は、各試行のたびに司令塔へ都度確認を求めず、B/A/S チームの判断で次の試行へ自動的に進めてよい。**司令塔判断を要するのは「上限到達時」または「必須KPI全達成で採用判断が必要になった時」のみ**とする
- 既存の改善ループ（SYS-FX007・008・010は完了済み、SYS-FX011は本ルール新設時点で改善ループ第7試行超過だが構造的な未達ゲートが残り採否判断が保留中）への遡及適用は行わない。本ルールは**本ルール新設日以降に起票される新規EXPから適用**する

### Q11: 執行判定タイムフレームの粒度（全SYS共通、恒久ルール）

**2026-08-28新設（EXP-FX000018 / SYS-FX024 の分解診断で発見）**。バックテストの約定判定を、シグナル生成と同じ足（H4等の粗い足）の高値・安値だけで行うと、**1本のバーが複数の価格水準を貫通したケースで、到達順序に依存する約定が体系的に取りこぼされる**。取りこぼしは常に楽観側（損失の過小評価）に働く。

SYS-FX024の実測では、同一パラメータ・同一期間・同一通貨で、

- H4足の高安のみで判定した探索診断: 損切り件数 10.3%、合計 **+23,734 pips**
- M5足で約定順序を解決した正式エンジン: 損切り件数 **19.1%**（68%増）、合計 **−13,551 pips**

と**符号が反転**した。1トレードあたりの平均損益はほぼ一致（TP +49.5→+50.1 pips、STOP −149.1→−143.8 pips）しており、差はすべて**件数構成**＝執行モデルに帰着した。正式エンジンの損切りのうち **21.2%（95/449）が同一H4バー内での建て→切り**であり、粗い足の判定ではこれが1件も記録されていなかった。

恒久ルール:

- **1本のシグナル足の中で複数回の約定が起こりうる戦略**（グリッド・ピラミッディング・複数レベルの指値/逆指値を同時に置く設計など）は、**約定判定を必ずシグナル足より細かい足（本PJではM5）で行う**こと。粗い足の高安のみによる判定は差し戻し。
- 同一の細かい足の中でなお利確と損切りが両方成立しうる場合は、**損切り優先**（保守側）を既定とし、spec に明記する。
- 探索的サニティチェック（正式プロトコル外）で粗い足の判定を使うこと自体は禁止しないが、**その結果を prescreen の根拠として提示する場合は「楽観側に偏る既知のバイアスがある」ことを必ず併記**すること。SYS-FX024 の prescreen は留保としてこの点を挙げていたが、影響の大きさ（符号が反転しうる規模）は想定できていなかった。

### Q12: 検証期間の拡張と代替データソースの正式利用（2026-08-28、司令塔判断）

**背景**: SYS-FX007〜024 の検証を通じ、`min_n_trades_effective ≥ 300` の未達が、
**戦略の優劣とは無関係に5戦略以上の判断を止めてきた**ことが判明した（OBS000012 §1）。

| 戦略 | 到達点 | 落ちた理由 |
|---|---|---|
| SYS-FX018 | KPI 7/9・ペイオフ 1.549（K4m 初クリア）・perm_p 0.044（有意） | **実効n 219 のみが未達** |
| SYS-FX012 | Train+Validation 13/18 | 未達3項目を自ら「いずれもサンプル数不足由来」と記録 |
| SYS-FX023 | 5/9 | 「実効n不足で正式な採否判断ができない」と明記して終了 |

本PJのスコープ「中期スイング・保有期間 数日〜数週間」と「Train 17ヶ月 × 4通貨で実効n 300」は
**構造的に両立しない**（1通貨あたり月4.4トレードが必要になる）。`min_n_trades = 300` は検出力
シミュレーションから正しく導出された値であり下げるべきではない。**下げるべきでないなら、
上げるべきは分子（＝検証期間）である。** なお n を通貨拡大で稼ぐ方向は SYS-FX016/019 で
「質が希薄化する」ことが実証済みであり、正しい方向は「銘柄」ではなく「時間」である。

**司令塔判断（2026-08-28）**: 「使ってよい（保守的コスト仮定を条件に）」。

恒久ルール:

1. **Dukascopy 公開ヒストリカルフィード（2018-11〜2023-10、GMO のデータ保持期間の壁より前・
   完全非重複）を、正式な Train 評価に使用してよい。** `fetch_dukascopy_h1.py` の
   「頑健性チェック専用、正式KPI評価には使わない」という旧方針は本項で上書きする
2. **コスト仮定は必ず保守側に倒すこと。** 2018〜2023 のスプレッドは現在より広かったと考えられる
   ため、拡張期間には現行スプレッドより不利な仮定を**結果を見る前に**事前登録し、
   **感度分析を必ず併記する**。楽観側の仮定で通すことは禁止する
3. **執行判定の粒度は Q11 に従う。** シグナル足より細かい足での約定判定が必要な戦略には、
   H1 ではなく M1→M5 再構成データ（`fetch_dukascopy_m5.py`）を使うこと
4. **データソース差の明記**: Dukascopy は GMO とは別ブローカーの BID 気配値である。
   また出来高0のバーを除外する仕様上、M5 バーが GMO より約2割少なくなる（低流動性帯が欠落する）。
   この差は結果に必ず併記する
5. **data dredging の防止（必須）**: 拡張データでの再評価対象は、**結果を見る前に**次の規則で
   機械的に限定する。
   - **対象に含める**: 「エッジ不在」ではなく「**サンプル数不足で判断保留**」と記録された戦略のみ
   - **対象に含めない**: 期待値が負・または明確に非有意と結論済みの戦略
   - **パラメータは再導出しない**。凍結済みパラメータをそのまま拡張期間に適用する
   - 拡張期間は **Train の延長として扱い**、既存の Validation / Test の凍結は維持する

### Q13: 評価の単位（単独戦略とポートフォリオ）（2026-08-28）

これまで全戦略を「**単独で**必須KPIゲートを全て通すか」で評価してきたが、SYS-FX024 の検証で
**「グリッドはトレンド局面で負け、ボラティリティ・ブレイク押し目は勝つ」という構造的な逆相関
（日次リターン相関 −0.22）が実測され、等ウェイト合成で月次シャープ 2.94→3.11・最大DD
10.08%→4.83% となる**ことが分かった（`research/method-notes/strategy_return_correlation.json`）。

恒久ルール:

- 単独戦略の必須KPI判定は**従来どおり維持する**（緩めない）
- それとは別に、**ポートフォリオとしての評価レイヤを設ける**ことを認める。単独では必須ゲート
  未達の戦略でも、**分散化オーバーレイとして採用候補になりうる**
- ただしポートフォリオ評価では以下を必須とする:
  - **配分ウェイトは結果を見る前に固定する**（等ウェイト、または逆ボラティリティ等の
    事前登録した規則）。結果を見てウェイトを調整することは HARKing であり禁止する
  - Train で観測された合成効果が **Validation で再現するか**を必ず確認する
  - 合成後のエクイティに対しても、単独戦略と同じ必須KPIゲートを適用する

### Q14: K5m の扱い、および K4m→PF 置換の恒久ルール化（2026-08-28、司令塔判断）

**背景**: EXP-FX000020（検証期間5年拡張）により、SYS-FX011/012/018/025 の4構成すべてが
拡張Train（実効n 533〜3,169）で permutation 有意（p=0.001〜0.035）を達成し、「サンプル数不足」
という説明が完全に否定された。残った未達ゲートは2つに収束した:

1. **K5m（スプレッドコスト倍率 ≥3.0）が全構成・全コスト水準で未達（実測1.52〜2.45）**。
   1トレードあたりの粗利益とコストの比であり、期間の長さ（サンプル数）と無関係に構造的に決まるため、
   サンプルを増やしても改善しない
2. **K4m（ペイオフレシオ ≥1.5）を、グリッドを含む合成（SYS-FX025）に対して PF ≥1.5 へ置換してよいか**
   （EXP-FX000018 §6.1 で単独グリッドに適用済みの論理の拡張。EXP-FX000019 amendment-01 §7で上程済み）

**司令塔判断（2026-08-28）**:

1. **K5m は維持する**（緩和しない）。「結果を見てから基準を動かさない」という本PJの運用原則、および
   K5m が「複利で残高が増えてもコスト前提が一定という仮定の脆さ」への安全マージンであるという性質
   （EXP-FX000020 §10.5）を優先する。この結果、**現行のコスト構造・戦略群（SYS-FX011/012/018/025）は
   原理的に採用ゲートに到達できない**という結論が確定する。次の一手はコスト構造そのものの改善
   （執行頻度を下げる・1トレードあたりのRを大きく取る等）または新カテゴリの戦略探索であり、
   既存戦略群のパラメータ再導出では解決しない
2. **K4m→PF置換を承認し、恒久ルール化する**。SYS-FX025 限定の例外ではなく、**グリッドを含む合成
   戦略全般**に適用する:
   - グリッドは構造上（勝ち=+1×step、負け=最大−N×step）ペイオフレシオ≥1.5を結果によらず達成
     不可能（EXP-FX000018 §6.1、結果を見る前に確定していた数学的事実）
   - この事実は合成にもそのまま一般化できる: 合成トレード群の一部がグリッド由来である限り、
     同じ構造的上限が合成全体のペイオフレシオを押し下げる
   - **恒久ルール**: グリッド戦略（またはグリッドを構成要素に含む合成戦略）の必須KPI判定では、
     K4m（ペイオフレシオ≥1.5）の代わりに **K4m'（Profit Factor ≥1.5）** を用いる。原形のペイオフ
     レシオは参考指標として記録は続ける。**グリッドを含まない単独戦略・合成には遡及適用しない**
     （K4mのまま判定する）

**適用結果**: K5m を維持した状態では、K4m→PF置換を適用しても**SYS-FX025 の最終分類は変わらない**
（判定に用いる保守的コスト水準×2.0では PF=1.379 と、置換後の基準1.5にも届かないため）。
EXP-FX000020 §10.2の「全4戦略・全3水準で『2_決着(不採用)』」という結論が、両論点の回答を経ても
そのまま確定する。

### Q15: min_n_trades の期間考慮と、n未達のまま採否を判断してよいか（2026-08-28、司令塔判断）

**背景**: EXP-FX000021（SYS-FX026）で、Train 9/9・Validation 8/9・Test 7/9 に到達した
一方、**Validation・Test の唯一（Testでは2つのうち1つ）の未達が実効n**だった
（355 / 91 / 121）。`min_n_trades = 300` は Train（約17ヶ月）の実測分布から
検出力シミュレーションで導出した値であり、これを **8ヶ月級の Validation / Test へ
そのまま適用すると、約半分の期間で同じ絶対件数＝約2倍のトレード頻度を要求する**
ことになる。本PJのスコープ（保有 数日〜数週間・4通貨）では、**戦略の優劣と無関係に
短い窓では原理的に達成できない**。

**司令塔判断（2026-08-28）**:

- **(a) n未達のまま採否を判断してよい。** フォワードだけで実効n 300 に到達するには
  月14トレード換算で約21ヶ月かかる（EXP-FX000021 amendment-03 §4）。n の充足を
  採否の必要条件にすると、本PJのスコープでは事実上いかなる戦略も採用に至らない
- **(b) n の閾値は期間を考慮する。**

**恒久ルール**:

1. **閾値を「基準窓あたり300件」と読み替え、評価窓の長さに比例させる。**
   基準窓は `min_n_trades` を導出した Train と同じ長さ（16.95ヶ月）とする。
   実装: `minmax_fx_dt.decision.criteria.min_n_trades_for_window(window_months)`

   | 窓 | 長さ | 従来の閾値 | **期間考慮後** |
   |---|---|---|---|
   | Train | 16.95ヶ月 | 300 | **300**（変わらず） |
   | Validation | 7.98ヶ月 | 300 | **141** |
   | Test | 8.44ヶ月 | 300 | **149** |

2. **水準（基準窓あたり300件）自体は緩めない。** 期間比例化は「同じ厳しさを窓の
   長さに合わせて表現し直す」ものであって、要求を下げるものではない
3. **必ず併記する但し書き（重要）**: 検出力80%という保証は **n の絶対値**に依存する。
   したがって期間比例化した閾値は「**その窓で戦略が想定どおりの頻度でトレードしたか**」
   を見る指標であり、「**弱いエッジを検出するのに十分な検出力があるか**」の保証ではない。
   **短い窓で新閾値を満たしても、統計的検出力そのものは不足したままである。**
   結果を報告する際は、期間考慮後の判定と併せて**実効nの実測値を必ず明記する**
4. **遡及適用**: 過去の確定済み判定（SYS-FX007〜025）は**再判定しない**。本ルールは
   本判断日以降の評価に適用する

**この変更が過去・現在の判定に与える影響（透明性のための実測、必ず記録する）**:

| 戦略 | 窓 | 実効n | 従来 | 期間考慮後 |
|---|---|---|---|---|
| SYS-FX026 | Train | 355 | PASS | PASS |
| SYS-FX026 | Validation | 91 | FAIL | **FAIL**（閾値141） |
| SYS-FX026 | Test | 121 | FAIL | **FAIL**（閾値149） |
| SYS-FX011 v7 trailonly | Validation | 133 | FAIL | **FAIL**（閾値141） |

> **本ルール変更は、SYS-FX026 を含むいかなる戦略の判定も覆さない。**
> 未達だった項目は期間を考慮しても未達のままである。結果を見た後の基準変更は
> 本PJが一貫して禁じてきたものであり、**この変更が自分に有利に働いていないことを
> 実測で示した上で**恒久ルール化する。

### Q16: 先読み（look-ahead）の検出と防止（全SYS共通、恒久ルール）

**2026-08-28新設（司令塔指示「先読みに関してルール化している筈だが、なぜ起きたか」への回答）**。

#### 背景 — なぜ必要か

`OBS000009` 不具合1（探索窓起点がH1バーの**始値時刻**+30分＝**確定30分前**）は、
**既存の防御をすべてすり抜けて SYS-FX026 の3期間すべての結果に載った**。
Test では純損益の **37.4%** がこの実行不可能なトレードから出ており、
除外すると事前登録した分類が **B → C（再現しなかった）へ反転**した。

根本原因の分析（実測で確認済み）:

| # | 何が無かったか | 具体的な事実 |
|---|---|---|
| ① | **先読みの品質ゲートが存在しなかった** | Q1〜Q15 の15項目に先読み／時間整合のゲートは1つも無い。Q2（ウォームアップ）は指標計算の話、Q11（執行判定粒度）は決済側の話で、いずれも「シグナル確定時刻 → エントリー可能時刻」を見ていない。**SYS-FX007 で先読みを発見した OBS000007（2026-08-15）は「そのバグを直した」で終わり、恒久ルール化されなかった** |
| ② | **先読み回帰テストが旧エンジン専用だった** | OBS000007 で追加した `test_sl_tp_not_triggered_by_future_price_within_same_h4_bar` の対象は `minmax_fx_dt.backtest.runner` / `simulator`。SYS-FX011/026 が使う `scripts/backtest_vol_breakout_dow_theory.py` には先読みテストが1本も無く、**エンジンを乗り換えたときに防御が引き継がれなかった** |
| ③ | **spec整合テストが「値」だけを見て「意味」を見ていなかった** | T-17（2026-08-22）で乖離検出のために新設した `tests/test_spec_consistency_vol_breakout_dow_theory.py` は `assert WINDOW_START_MIN == 30  # ブレイクバー確定後30分` としており、**定数30は正しく、バグは「何から30分か」という基準点にあった**ため pass し続けた。コメントに正しい仕様が書かれていたことが、かえって誤った安心感を与えた |
| ④ | **既知の不具合が未解決のまま新規評価が走った** | OBS000009 は2026-08-27に発見・影響量まで実測済みだったが、`70対応待ち/` に「司令塔判断待ち」で置かれチェックボックス未着手のまま、**翌日 SYS-FX026 の全評価が実行された**。「未解決の先読みがある戦略系統で新規評価を始めない」というルールが無かった |
| ⑤ | **記録は残っていたが読まれなかった** | 不具合1は `ACTIVE.md` の110行目に技術的詳細まで正しく記録されていた。しかし ACTIVE.md は **330行・約53,000トークン**に肥大化し、セッション開始時の読み込みが打ち切られて到達しなかった。外部レビュー（2026-08-20）が指摘した「記録は残っていたが次の作業に反映されなかった」の再発 |

#### 恒久ルール

**R1. 先読み検出を必須の品質ゲートとする。**
すべての戦略について、**シグナルが確定する時刻 ≤ エントリーが可能になる時刻**を機械的に検証する。
違反があれば結果の如何によらず**差し戻し**とする。特に次を必ず確認すること:

- **バーのインデックスが「始値時刻」か「確定時刻」か。** pandas の `resample()` は
  `label` 既定が `left`（＝始値時刻）である。**`+ N分` の起点を書く前に必ず確認する**
- 集約足（H1/H4/D1）の高値・安値・終値を使う判定は、**そのバーが閉じるまで使えない**
- 指標（ATR・ADX 等）の値も同様に、確定バーまでしか使えない

**R2. 先読み回帰テストはエンジンごとに必須とする。**
新しいバックテストエンジン（`scripts/backtest_*.py` 含む）を追加した場合、
**先読みテストの移植を完了条件とする**。既存エンジンのテストがあることをもって
新エンジンの防御とみなしてはならない。

**R3. spec整合テストは「値」ではなく「意味」を検証する。**
定数の一致だけを assert するテストは、**基準点・単位・時刻の意味の取り違えを検出できない**。
時刻・期間・基準点に関わるパラメータは、**合成データで実際に実行し、生成された
トレードの時刻を検証する**形にすること。
（実装例: `tests/test_lookahead_entry_window.py` — 定数ではなくエントリー時刻を検証する）

**R4. 未解決の先読み・データ整合不具合がある戦略系統では、新規の正式評価を開始しない。**
`70対応待ち/` に当該系統の未解決項目（チェックボックス未着手）がある場合、
**その系統の新規 Train/Validation/Test 評価およびフォワード投入を開始してはならない**。
先に決着させるか、司令塔が明示的に「不具合を含んだまま進める」と判断し、
**その旨を評価の事前登録に明記**した場合のみ進めてよい。

**R5. セッション開始時に `70対応待ち/` の未解決項目を確認する。**
`CLAUDE.md` のセッション開始ルーチンに追加する（本ルールと同時に反映済み）。
あわせて **`ACTIVE.md` の肥大化を防ぐ**（下記 Q17）。

#### 既知の未決事項（本ルール新設時点）

`simulate_dow_theory_trend()` に `bar_close_anchored` パラメータを新設し、
**SYS-FX026 は修正版（True）で再評価する**。ただし**既定は False（旧挙動）に据え置いた**。
理由は、稼働中の SYS-FX012 フォワードテストを含む既存戦略の結果を無断で変えないため。

**既定を反転するか（＝SYS-FX011/012 など既存戦略も修正版で再評価するか）は
`OBS000009` として司令塔判断を仰ぐ。** 判断が出るまで、新規の正式評価では
`bar_close_anchored=True` を明示指定すること。

### Q17: 進行記録（ACTIVE.md）の肥大化防止（2026-08-28、恒久ルール）

Q16 ⑤ のとおり、**`ACTIVE.md` が330行・約53,000トークンに肥大化し、セッション開始時に
読み切れなくなっていた**ことが、既知の不具合を見落とした直接の原因の一つである。
「記録すれば伝わる」は、記録が読める大きさである限りにおいてのみ成立する。

恒久ルール:

- **`ACTIVE.md` の冒頭に「未解決ブロッカー」セクションを置く。** `70対応待ち/` の
  未着手項目と、進行中の実験が抱える既知の不具合をここに集約する。
  **セッション開始時にまずここを読む**
- **「直近の状態」の詳細ログは、当月分のみ `ACTIVE.md` に置く。**
  それ以前は `research/archive/ACTIVE-YYYYMM.md` へ移し、リンクのみ残す
- 目安として **`ACTIVE.md` は 200行以内**に保つ
