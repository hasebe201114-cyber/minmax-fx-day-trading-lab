# PJ000004 - 基本データ層と検証プロセス定義（minmax-fx-day-trading-lab）

> 担当: A 設計チーム（spec 確定）+ S 戦略チーム（プロセス監督）
> lp-strategy-lab の PJ000004 相当のドキュメント。本PJ固有の品質ゲート Q1〜Q8 とデータ層を定義する

## 1. 背景

LP 戦略ラボでは「データの壁」（DS-1〜DS-6 の精度不足が複数実験の判定を覆した事例）から、検証プロセス自体を再設計する PJ000004 を実施した。FX デイトレードでも同等のリスクがあるため、**プロジェクト起票と同時に**データ層と品質ゲートを明文化する。

## 2. データ層（DS-FX シリーズ）

| ID | 名称 | 主ソース | 検証粒度 | 必須度 |
|---|---|---|---|---|
| **DS-1** | 通貨ペア × 足種 × 期間の OHLCV | dukascopy / histdata.com / GMO API | 3年 / 1分足以上 | 必須 |
| **DS-2** | スプレッド時系列（ティック or 1分粒度） | GMO 実測 | 6ヶ月 / 1分粒度 | 必須 |
| **DS-3** | 経済指標カレンダー + 発表時刻周辺挙動 | investing.com / ForexFactory | 3年 / イベント単位 | 必須 |
| **DS-4** | セッション境界時刻 + 典型ボラ/出来高 | 自前集計（DS-1 から派生） | 3年 / 1時間粒度 | 必須 |
| **DS-5** | スリッページ代表性データ | GMO テストネット or 0.5 pip 固定フォールバック | 100注文以上 | 必須 |
| **DS-6** | GMO コイン API 仕様 | GMO 公式ドキュメント | n/a | 必須 |
| DS-7 | （将来）代替ブローカー仕様（OANDA / IBKR） | 公式 | n/a | 将来 |

## 3. 品質ゲート Q1〜Q8

### Q1: データ欠損の網羅的検出
- 1分足について全カレンダー日から**価格パスの欠損**を検出
- 経済指標発表時刻の周辺 ±30 分に欠損があれば警告
- 週末/祝日の正常な欠損は除外

### Q2: ウォームアップ期間の前倒し
- 移動平均/RSI 等のインディケータは計算に N 期間必要
- **検証区間の最初の N 期間は必ずウォームアップ**として結果から除外
- ウォームアップを除外しない実装は差し戻し

### Q3: 平滑化系列の併記
- 生の OHLC に加え、ATR/ADX/標準ボラ等の平滑化系列を併記
- 単一指標のみの K ゲートは不可

### Q4: implied コスト（スプレッド + スリッページ）の自動反映
- バックテストは**成行で約定したと仮定 + スプレッド + 0.5 pip スリッページ**を毎回課す
- `params.json` で cost_pips_per_side = 0.5 を明示
- cost_pips_per_side = 0 は差し戻し

### Q5: データソース/取得日の記録
- `data/curated/*.json` の各ファイルに `source` / `fetchedAt` を必須記載
- `data/MANIFEST.json` で全データ系列を一元管理

### Q6: 通貨ペア単位の decimals 整合性
- USD/JPY は 0.001、EUR/USD は 0.00001 等、JPY 系と非 JPY 系で桁数が異なる
- ロットサイズ・P/L 計算時の桁数誤差を CI で検出

### Q7: 当日クロースの保証（デイトレード固有）
- 検証区間内のすべてのトレードは**必ず日本時間でその日の 06:00 までに手仕舞い**（または対応するセッションクローズ時刻）
- それ以降にクローズされたトレードが含まれていれば差し戻し
- 週末持ち越しは絶対禁止

### Q8: ブローカー仕様の整合性（デイトレード固有）
- 通貨ペアの取扱状況が GMO コイン 21 ペアに含まれているか
- 取引単位（最小/最大ロット）、スプレッド、レバレッジ、API rate limit が spec と一致するか
- API 仕様変更時の追跡可能性（`data/curated/ds-6-api-spec.json` の fetchedAt）

### Q9: 最大DD（ドローダウン）の定義（全SYS共通、恒久ルール）

**2026-08-21新設（EXP-FX000005外部レビューT-10対応）**。ポジションサイジング方式によって、
最大DDを「初期資金比」「ピーク（直近最大残高）比」のどちらで評価すべきかが異なる。
**この選択は結果を見る前に固定すること**（結果を見た後に変更した場合は`00-spec.md`に
理由・日付・影響を受ける過去の判定を明記すること）。

| サイジング方式 | DD定義 | 理由 |
|---|---|---|
| 固定ロット（残高に依存せず一定通貨量） | **初期資金比** | 複利で残高が変動しても1トレードのリスク量は変わらないため、初期資金を基準にした比率がそのまま実質的なリスク量を表す |
| 複利（残高の一定%をリスクに充てる） | **ピーク比**（直近の最大残高からの下落率） | リスク量自体が残高に比例して変動するため、初期資金比で評価すると、複利で資産が大きく増えた後の変動を実態より過大に見せてしまう（絶対額としては同じ下落でも、初期資金比では常に大きな%になる） |

**過去システムへの適用可否（2026-08-21確認）**: SYS-FX007（`src/minmax_fx_dt/backtest/simulator.py`の`lot_size`固定）・SYS-FX008・SYS-FX009（同エンジン踏襲）・SYS-FX010（`backtest_carry_no_stop_tvt.py`「固定ロット(1lot=1000通貨)」明記）は**いずれも固定ロット方式**であり、初期資金比のDD定義は当時から正しかった。**遡及的な再評価は不要。** SYS-FX011（EXP-FX000005）のみ`risk_pct_per_trade`（残高の1%）による複利サイジングを採用しており、ピーク比DDへの切り替えが必要だった（`01-trade-scenario-definition.md`§6、`evaluate_vol_breakout_dow_theory_kpi.py`の`peak_relative_max_dd_pct()`/`peak_relative_monthly_max_dd_pct()`、および`src/minmax_fx_dt/backtest/metrics.py`の同名関数を参照）。

### Q10: 改善ループの停止条件（全SYS共通、恒久ルール）

**2026-08-21新設（EXP-FX000005外部レビューT-19対応）**。SYS-FX008には「3試行で停止」という上限があった一方、SYS-FX011は明確な上限なしに改善ループが第7試行まで進み、そのたびに「司令塔判断待ち」で止まる運用になっていた。これは「ユーザのオペレーションは最低限に」という開発方針と整合しないため、**Phase 2（prescreen）起票時に上限回数を事前登録する**ことを恒久ルールとする。

- **既定上限**: 改善ループ**5回**（結果を見て採否/設計変更を決めた試行のみをカウント。カウント方法はT-18の試行数え方に準拠し、既知のバグ修正・検定手法自体の是正・外部レビュー対応の修正はループ回数にカウントしない）
- 起票時にSYSTEMS.mdの戦略複雑度に応じて上限を調整してよいが、**結果を見る前に**`00-prescreen.md`または`00-spec.md`に明記すること
- **上限に達し、かつ必須KPIゲート（K1m〜K7m相当）が未達のままの場合、自動的にREJECT（不採用）確定とする**。追加の試行を行いたい場合は新規EXP番号を起票し、そこで新たにループ回数をゼロから起算する
- 上限到達前は、各試行のたびに司令塔へ都度確認を求めず、B/A/S チームの判断で次の試行へ自動的に進めてよい。**司令塔判断を要するのは「上限到達時」または「必須KPI全達成で採用判断が必要になった時」のみ**とする
- 既存の改善ループ（SYS-FX007・008・010は完了済み、SYS-FX011は本ルール新設時点で改善ループ第7試行超過だが構造的な未達ゲートが残り採否判断が保留中）への遡及適用は行わない。本ルールは**本ルール新設日以降に起票される新規EXPから適用**する

### Q11: バックテストエンジンのアーキテクチャ分離（データ生成/シミュレーション部とトレードエンジン(本番相当)部、恒久ルール）

**2026-08-26新設**。N_BREAKOUT値動き分析(`scripts/analyze_n_breakout_price_movement.py`)の過程で、
SYS-FX011/SYS-FX012系列の全バックテストスクリプトが共通して使う`h1.index[break_idx]`が、
pandas `resample('1h')`の既定ラベル(バーの**開始**時刻)を「バー確定時刻」として扱っており、
実際のバー確定(終了)時刻より最大1時間早い先読みを含んでいたと判明した。自然実験
(`scripts/analyze_h1_confirm_time_lookahead_impact.py`)で定量化した結果、SYS-FX012の
現行凍結設計(候補①、フォワードテスト実施中)のTrain評価が、この1点の修正だけで
Profit Factor 1.87→1.04・permutation p値0.031→0.455(有意→非有意)・必須KPI達成数7/9→1/9・
総リターン+172%→-4%まで劣化することを確認した(詳細:
`research/method-notes/h1_confirm_time_lookahead_impact.json`)。

**根本原因**: 現行のバックテストエンジンは「全期間のヒストリカルDataFrameをそのまま保持し、
戦略ロジックが任意の時点から任意の(未来を含む)インデックスへ自由にアクセスできる」設計に
なっており、"ある時刻において、どのデータが実際に確定・利用可能だったか"を管理する責任を
コード側のどこも負っていない。そのため、日付演算(バー確定時刻の計算)を1箇所間違えるだけで、
戦略ロジックが未確定データを参照してしまう。

**方針**: 今後新規に構築するバックテスト検証プログラムは、以下の2層に構造分離することを
恒久ルールとする。

1. **データ生成/シミュレーション部**: 過去の市場データ(ヒストリカルOHLCV)を、実際の相場で
   その情報が確定するタイミング通りに、時系列順に一本ずつ「配信」する層。責務は「現在時刻
   において、どのバーまでが確定済みか」を正しく管理することのみ(例: H1バーは開始時刻ではなく
   終了時刻(=開始+バー長)に初めて配信可能になる)。時間軸(M5/M15/H1/H4/D1/W1)ごとに確定
   タイミングを一元的・明示的に扱う。
2. **トレードエンジン(本番相当)部**: シミュレーション部から配信された「確定済みデータ」の
   みを入力として受け取り、検出・エントリー・エグジット判定を行う層。設計上、まだ配信されて
   いない未来のバー/未確定のバーには**参照する手段自体が存在しない**ようにする(全期間の
   DataFrameを直接渡さない、都度配信された分のみを保持するイテレータ/ジェネレータ型の
   インターフェースにする等)。この層は将来的に本番(ライブ)実行にそのまま転用できることを
   目指す(=バックテストと本番で同一のトレードエンジンコードを使う)。

この分離により、「戦略ロジックが誤って未確定データを参照する」という種類の先読みバグは、
コードの構造上原理的に発生しなくなる(現状のように"時刻計算を1行間違える"ことで発生する
余地がなくなる)。

**適用範囲**: 本ルール新設日(2026-08-26)以降に新規着手するバックテストエンジン/検証
プログラムに適用する。既存のSYS-FX007〜022系列のエンジン(`src/minmax_fx_dt/backtest/`・
`scripts/backtest_*.py`)を遡及的にこの構造へ移行するかどうかは別途大規模作業であり、
本ルール新設だけでは移行を義務付けない。SYS-FX011/SYS-FX012の先読み問題自体への対応
(パラメータ再導出・Validation再検証・フォワードテスト一時停止の要否等)も別途、
上記JSONを踏まえた司令塔判断待ちとする。

## 4. 検証プロセス

### Phase 1: データ基盤（DATA-FX チケット）
- 目的: DS-1〜DS-6 を取得・検証・カタログ化
- 担当: A 設計（spec）→ B 実装 → C 品質（DATA モード）
- 完了条件: 全 Q1〜Q8 合格、`data/curated/*.json` 実体化、`MANIFEST.json` 完成

### Phase 2: 戦略 prescreen
- 目的: SYSTEMS.md の各 SYS について GO/PAUSE を S が断じる
- 成果物: `research/EXP-FXxxxxx/00-prescreen.md`

### Phase 3: 詳細 spec 確定
- 目的: K1d〜K6d の閾値を**バックテスト結果を見る前に**固定
- 成果物: `research/EXP-FXxxxxx/00-spec.md`

### Phase 4: バックテスト → フォワードテスト → 採用判定
- 目的: 6ヶ月バックテスト + 30/60/90 日フォワードテスト
- 成果物配置規約（**2026-08-21新設、EXP-FX000005外部レビューT-20対応、全SYS共通の恒久ルール**）:
  - `research/EXP-FXxxxxx/10-result/`: **最終的に確定したパラメータのみ**を格納する小規模なJSONスナップショット（例: `trail_multiplier.json`・`trend_follow_params.json`・`double_pattern_params.json`）。「この戦略はこのパラメータで検証した」という監査証跡として、改訂の都度上書きせず追加する。
  - `research/method-notes/`: バックテスト結果・診断分析・KPI評価など、改善ループの過程で反復的に生成される成果物（`_backtest.json`・`_kpi_evaluation.json`・各種`analyze_*.py`の出力）を格納する。ファイル名にversion/variant識別子（`_v7`・`_t08fix`等）を含めて上書きせず履歴を残す。
  - 20-c-review.md・30-decision.mdは`research/EXP-FXxxxxx/`直下（従来通り）。
  - **経緯**: EXP-FX000001（SYS-FX007）は`10-result/`に結果を集約していたが、EXP-FX000002（SYS-FX008）以降は次第に`research/method-notes/`側へ実質的な成果物が移り、EXP-FX000004（SYS-FX010）・EXP-FX000005（SYS-FX011）では`10-result/`が最終確定パラメータのみ（EXP-FX000005では未使用）という状態に自然に収斂していた。この実態を追認する形で正式ルール化する。
  - `.gitignore`の`!research/**/10-result/run.log`（run.logの追跡強制）は、EXP-FX000004・EXP-FX000005ではrun.log自体を生成しないため対象外。今後`run.log`を使わないEXPは、この例外規定に従う必要はない。
