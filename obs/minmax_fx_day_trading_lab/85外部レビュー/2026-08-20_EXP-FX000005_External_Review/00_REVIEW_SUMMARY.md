# 0. 結論が変わりうる発見（最優先）

## F1. 週末強制クローズが一度も発動していない

### 事実

`research/method-notes/vol_breakout_dow_theory_4pairs_v6_1000usd_backtest.json` の `exit_reason` 集計:

```
train      Counter({'SL_INITIAL_NO_TP': 125, 'TP_THEN_SL_TRAIL': 125, 'TP_FULL': 95})
validation Counter({'SL_INITIAL_NO_TP': 44,  'TP_THEN_SL_TRAIL': 41,  'TP_FULL': 19})
test       Counter({'SL_INITIAL_NO_TP': 69,  'TP_THEN_SL_TRAIL': 59,  'TP_FULL': 44, 'MAX_HOLD': 1})
```

`WEEKEND_NO_TP` / `TP_THEN_WEEKEND` が **3 期間とも 0 件**。一方、エントリー時刻と決済時刻から
土曜 06:00 JST を跨いだトレードを数えると:

```
train:      n=345 週末跨ぎ=27 (7.8%)
validation: n=104 週末跨ぎ= 6 (5.8%)
test:       n=173 週末跨ぎ= 8 (4.6%)
合計 622 件中 41 件 (6.6%)
```

典型例（train 1 件目）:

```json
{"pair": "USD_JPY", "direction": "DOWN",
 "entry_time": "2023-11-03 21:40:00+09:00",   // 金曜 21:40
 "exit_time":  "2023-11-06 21:00:00+09:00",   // 月曜 21:00
 "exit_reason": "SL_INITIAL_NO_TP", "r_gross": -1.0}
```

### 原因

`scripts/backtest_vol_breakout_dow_theory.py`:

```python
def is_weekend_close_time(ts: pd.Timestamp) -> bool:
    return ts.weekday() == 5 and ts.hour >= 6
```

この判定は `simulate_scaled_scheme()` のループ内で **H1 バーの時刻に対して**評価される。しかし
DS-1 は GMO の klines を JST に変換したもので、市場は土曜 06:00 JST 前後に閉まるため、
**「土曜 06:00 以降の H1 バー」がデータに存在しない**。よって条件は一度も真にならない。

### 影響

1. PJ 共通ルール「週末持ち越し禁止」および `01-trade-scenario-definition.md` §2・§4.7 の記述が、
   実装によって保証されていない（ドキュメントと実装の乖離）。
2. 週末ギャップリスクが損益に反映されていない。しかも上記の例のようにストップは
   **週明けギャップを無視して、正確なストップ価格で約定した扱い**になっている（→ 3. の指摘と複合）。
3. 6.6% のトレードが本来存在しないはずのもの、または本来と異なる損益になっている。

### 対処

`is_weekend_close_time()` を「土曜 06:00 以降のバーで発動」ではなく
**「週内の最終バー（次のバーが週明けになるバー）で強制クローズ」** に変更する。
`src/minmax_fx_dt/backtest/simulator.py:420` の同名ロジックにも同じ欠陥がないか併せて確認すること
（SYS-FX007〜010 の過去判定にも波及しうる）。

## F2. `permutation_p < 0.05` は 4 通貨構成では原理的に達成不能

### 事実

`permutation_test_clustered()` は、**通貨ペアごとに符号を 1 個だけ引き、そのペアの全トレードに一括適用**する:

```python
pair_signs = np.where(y >= 0.0, 1.0, -1.0)   # (n_permutations, k)  k = 通貨ペア数
signs = pair_signs[:, trade_pair_idx]        # 同一ペアの全トレードに同じ符号
```

したがって検定の実効標本サイズは「トレード数」ではなく **「通貨ペア数 = 4」**。
さらに JPY クロス 4 本は平均相関 0.808（実効独立数 1.168）。

プロジェクトの関数をそのまま呼び出して測定した結果:

| ケース | n | p 値 |
|---|---|---|
| 4 通貨・全トレード勝ち（mean_R = +1.0、理論上最強のエッジ） | 100 | **0.3158** |
| 同上 | 1,000 | **0.3158** |
| 同上 | 20,000 | **0.3158** |
| 4 通貨・勝率 60% / ペイオフ 1.0 | 100〜20,000 | **0.4473**（一定） |
| 5 通貨・全勝 | 1,000 | 0.1469 |
| 単一通貨・全勝 | 100 | 0.00005 |

**p 値の下限が 0.3158 で、n をいくら増やしても 1 桁も動かない。**

### 影響

1. 報告されている `p = 0.3866 / 0.4625 / 0.4705` は、戦略の情報をほぼ含んでいない。
   「統計的有意性が示せていない」（§11 課題 4）のは戦略の性質ではなく **検定の性質**である。
2. KPI 10 項目のうち 1 項目が構造的に永久 FAIL する。「5/10・2/10・6/10」という数字の解釈が歪む。
3. `permutation_test_clustered()` は 2026-08-18 追加なので、SYS-FX010 以降の判定に効いている。
   SYS-FX007/009 は独立符号版のため本件の影響外だが、`portfolio-ledger.md` の
   「SYS-FX008 の USD/JPY 単独 perm_p=0.058」が唯一情報量のある数字だった、という読み替えが必要。
4. §11 課題 4 の記述「帰無分布が離散的（最大 32 通り）で分解能が粗い」は問題を過小評価している。
   分解能の粗さではなく **検出力がゼロ** であることが問題。

### 対処

検定手法を差し替える。推奨は次のいずれか:

- 日次（またはトレンドイベント単位）の戦略 PnL 時系列に対する **stationary bootstrap**
- トレードの **ブロック順列**（クラスタ = 日、または同一トレンドイベント）

いずれも「同時刻に複数通貨で建つ」という実際の依存構造を捉えつつ、帰無分布の分解能を潰さない。
現行の「D1 リターン相関をガウス・コピュラに入れてペア単位で符号を引く」方式は、
依存構造の捉え方として粗すぎ、かつ検出力を消している。

## F3. ATR トレーリングストップが事実上一度も作動していない

### 事実

全期間プールの `exit_reason` 別 `r_gross` 分布:

```
SL_INITIAL_NO_TP:  n=238  中央値 -1.000  平均 -1.000  min -1.00  max -1.00
TP_THEN_SL_TRAIL:  n=225  中央値 +0.400  平均 +0.730  min +0.40  max +1.53
TP_FULL:           n=158  中央値 +2.100  平均 +2.100  min +2.10  max +2.10
MAX_HOLD:          n=1
```

`TP_THEN_SL_TRAIL` 225 件の内訳:

```
r_gross = +0.400 ちょうど（TP1 のみ到達 → 建値ストップ）: 51.6%
r_gross = +1.100 ちょうど（TP1+TP2 到達 → 建値ストップ）: 37.8%
                                                  合計   89.3%
最大値                                                    +1.53
```

### 原因

`atr_trail_multiplier = 3.23` は SYS-FX009 の **H1 設計**（`derive_double_pattern_params_h1.py`）から
転用した値。しかし本戦略の 1R は **M5 スケール**（`pivot ± 0.703 × ATR(M5)`）である。

実測 `leverage_ratio = entry_price / initial_risk` の中央値は 826 なので、
USD/JPY 150 円なら 1R ≈ 0.18 円 ≈ 18pips。一方 `3.23 × ATR(H1)` は概ね **3〜4R 相当**。
トレーリングストップは常に現在値から 3〜4R 下（UP 方向）に置かれるため、
**TP3 = 4R の全量利確に先に到達し、原理的に噛まない**。

### 影響

1. `01-trade-scenario-definition.md` §5.3 で「TP1 到達以降、残存ポジションに ATR トレーリングを適用する」
   と記述されている出口は、**実際には「段階利確＋建値ストップ」のみ**。定義書が実装の挙動を表していない。
2. 「トレーリングで利を伸ばす」という設計は **まだ一度も検証されていない**。
   §11 課題 5「ペイオフレシオが 1.0 近辺」の直接原因がこれである可能性が高い。
3. 改善ループ第 6 試行で TP3 を 3R → 4R に上げた効果の解釈も、トレールが効いていない前提で読み直す必要がある。

### 対処

`atr_trail_multiplier` を **ATR(M5) 基準で再導出**する（1R の 0.5〜1.5 倍程度のレンジで）。
そのうえで「段階利確を外し、建値＋トレーリングだけで伸ばす」構成を 1 本、比較対象として立てる。

# 1. 戦略について

## 1-1. 出口設計と KPI の型が矛盾している（K4m が算術的にほぼ不可能）

F3 の結果、損益分布は実質的に 4 値の離散になっている:

| 値 | 意味 | 構成比（全期間 622 件） |
|---|---|---|
| −1.00R | 初期 SL | 38.3% |
| +0.40R | TP1 のみ → 建値 | 18.6% |
| +1.10R | TP1+TP2 → 建値 | 13.7% |
| +2.10R | TP_FULL（0.4×1 + 0.35×2 + 0.25×4） | 25.4% |

勝ちトレードの平均は **1.295R**、負けは常に厳密に −1.00R。したがってペイオフ比の上限がここで頭打ちになる。
K4m（≥ 1.5）を満たすには勝ちの約 65% が TP_FULL に到達する必要があり、構造的に届かない。

**現状は「高勝率・低ペイオフ型に舵を切ったのに、低勝率・高ペイオフ型の基準で採点している」状態。**
取るべきはどちらかである:

- **(a)** TP1 の 1R 部分利確と建値移動をやめ、トレール幅を ATR(M5) 基準に張り替えて「伸ばす」設計に戻す
  （K4m を満たしにいく）
- **(b)** 本戦略に K4m を非適用と宣言し、期待値・PF で評価する

現状は (a)(b) どちらも取っていないため、両方に負けている。F3 により (a) は**まだ試されていない**ので、
1 回試す価値が高い。

## 1-2. エントリーは M5、決済判定は H1 という粒度ミスマッチ

`simulate_scaled_scheme()`:

```python
start = entry["entry_idx"] + 1   # entry_idx = M5 エントリー時刻を含む H1 バー
```

**エントリーした H1 バーの残り（平均約 30 分）が完全に不可視**である。
M5 スケールのストップ（1R ≈ 18pips）と TP1（= 1R）が両方この窓に入る頻度は高いはずで、
バイアスの方向も大きさも未検証のまま結果に乗っている。

エントリーが M5 なら決済も M5 で回すべき。これは F1・F3 と並んで
「直してから議論を再開すべき」項目である。

なお、バー内順序の扱い（SL 判定 → 建値トリガー → TP 判定 → トレール更新）は
SL 優先＝保守的で、この点は適切。

## 1-3. 唯一再現しそうなエッジは「H1 継続確認後の再開」の方

`entry_exit_diagnostics.json` で有意だった所見は事実上 1 つ（型崩れ追跡開始からの経過 M5 バー数、
perm_p = 0.025、**多重検定未補正**）。一方、

> H1 継続確認後の再開エントリーは SL 率 36.1%、非再開 42.6%

はメカニズムの説明も付く数少ない構造である。

検出層を「H1 のボラティリティ・ブレイク」ではなく **「H1 のトレンド継続そのもの」** に置いた設計を
1 本立てる価値がある。ブレイク検出（N=3.5）はエントリー機会を絞る（= 実効 n 不足の主因）だけで、
それ自体がエッジの源泉である証拠は本検証を通じて出ていない。

## 1-4. 実質レバレッジとロスカット判定

`leverage_ratio = entry_price / initial_risk` の実測:

```
中央値 826.1 / p90 2,183.8 / 最大 8,957.8
→ 実質レバレッジ = risk_pct × leverage_ratio = 中央値 8.3 倍、p90 21.8 倍
→ 25 倍キャップの発動は 622 件中 49 件（7.9%）
```

M5 スケールの狭いストップは必然的に高レバになる。GMO の証拠金維持率（ロスカット）判定を入れた
シミュレーションが未実施で、**DD が基準内でも途中でロスカットに刈られる経路**が評価されていない。
`skipped_ruin` フラグはあるが、証拠金維持率ベースの強制決済はモデル化されていない。

## 1-5. 未着手の「通貨ペア拡大」が、実は最も費用対効果が高い

改善ループ第 4 試行の総括は「実効サンプル数を増やす調整は一貫して品質を犠牲にする」だが、
それは **同じ通貨・同じ時間軸の中で閾値を緩めた**からである。

通貨ペア拡大（§11 課題 9、④として未着手）は質を落とさず n を増やせる唯一の方向であり、
さらに **非 JPY ペア（GBP/USD・EUR/GBP・AUD/USD 等）を入れると実効独立数が上がり、
F2 の permutation 分解能も同時に改善する**。ここだけは未検証のまま残すべきではない。

## 2-3. `min_n_trades = 300` と実効 n 係数の二重計上

`compute_n_trades_effective()` は `n_eff = 名目n × (N_eff_pairs / n_pairs)`。
4 通貨 JPY クロスでは:

```
N_eff_pairs = 4 / (1 + 3 × 0.80822) = 1.168  →  係数 0.292
n_eff = 300 に必要な名目トレード数 = 1,027 件
```

Test 期間 8.5 ヶ月・4 通貨なら **1 ペアあたり月 30 トレード**。
これは「週 1 回程度の高ボラを厳選する」という戦略コンセプトと **定義上両立しない**
（`00-prescreen.md` の想定では Train 74 週 × 5 通貨で母数上限 370 件）。

さらに `MIN_N_TRADES_STATISTICAL = 300` 自体は `min_n_trades_power_analysis.json` の
**独立トレード前提**の検出力シミュレーション（勝率 60%）から出た値である。
同じ分析は勝率 50.95%（K5m 相当のエッジ）では **n = 4,000 でも検出力 0.19** と示しており、
300 という閾値は「勝率 60% という強いエッジ」を前提にした楽観値。
そこへさらに相関ハンデを掛けると、相関の罰則が二重に効く。

**対処:** 相関補正は「n」と「検定」のどちらか一方に入れる。両方に入れない。

## 2-4.「10 項目中 X」という達成数スコアが事前登録の判定ルールを侵食している

`00-spec.md` の KPI 表は閾値のリストであり、本来は全項目クリアが条件だったはず。
それが「5/10・2/10・6/10」という連続尺度に化けたことで、「改善している」と語れる余地が生まれた。
第 6 試行の総括が「KPI 達成数は不変だが質的指標は改善」で終わっているのは、その副作用。

**対処:** 必須ゲート（hard gate）と参考指標を明示的に分ける。
現状の定義のままでは K3m・K4m・permutation は参考指標にすらならない（2-1〜2-3、1-1 参照）。
必須は「Validation の月次期待値が正」「PF」「DD（ピーク比）」の 3 つに絞るのが現実的。

## 2-5. コストモデル: SL・トレーリングの「指値・スリッページ 0」は実務的に誤り

司令塔の「SL、トレーリングも指値注文でよい」という指示に従った結果だが、
**逆指値注文はトリガー後は成行と同じ性質**で、価格保証はない。しかも発動するのは
定義上、高ボラ局面である。

`00-spec.md` の記録によれば、この変更だけで **Train +443.8% → +530.2%**（約 90 ポイント）動いている。

さらに F1 と複合すると、週末ギャップを跨いだ 41 件も「ストップ価格ちょうどで約定」している。

**対処:**
- SL / トレールに 0.5〜1.0pip（高ボラ時はより大きく）のスリッページを戻す
- 週末ギャップは別途モデル化する（金曜終値 → 月曜始値のギャップ分布から）

指示に忠実であることと、実行可能性を確認することは両立させるべき。

## 2-6. DD 定義の是正は結論として正しいが、変えたタイミングが悪い

「複利サイジングならピーク比」という司令塔の指摘は妥当である。ただし
**「初期資金比で FAIL」という結果を見た後に**変わった。

**対処:** 「複利サイジング戦略はピーク比、固定サイジングは初期資金比」を全 SYS 共通の事前定義として
`criteria.py` に固定し、SYS-FX007〜010 の過去判定にも遡って適用可否を記録する。

## 2-7. Validation の弱さの本質

`v6` の Validation は 総リターン +12.57% / PF 1.272 / mean_r_net +0.126 と正だが、
**月次シャープ −0.494・月次期待値が負**。つまり **大半の月は負けで、少数の月で稼いでいる**。
§11 課題 3 は「地政学ショック混入の影響」と説明しているが、
分布の形（少数の大勝ち依存）そのものが本質的な弱点であり、
これは 1-1 の「高勝率・低ペイオフ型」という設計選択と整合しない（本来は逆の形が出るはず）。
月次ではなく週次・日次で期待値の符号を確認し、どの粒度から正になるかを見るべき。

# 3. プロセスについて

## 3-1. Test が 6 周のループで 10 回以上参照されている ＝ もうホールドアウトではない

`00-spec.md` を追うと、Test は少なくとも以下で評価されている:

1. 第 1 試行の $1,000 TVT
2. コストモデル精緻化 第 1 段階
3. 同 第 2 段階
4. 1 通貨 1 ポジション制約修正後
5. 正式 KPI 判定（初期資金比 DD）
6. 4 通貨版
7. DD 評価ピーク比への修正後
8. カレンダー版（第 3 試行）
9. 第 4 試行 Part A
10. 第 4 試行 Part B
11. 第 5 試行
12. 切り分け比較（3 バリアント）
13. 第 6 試行

**「Test 6/10」は選択バイアス込みの数字**であり、汎化性能の推定値として使えない。
Train 5/10 → Validation 2/10 → Test 6/10 という並びを見て「Test が良いから見込みがある」と読むのは、
いま最も危険な読み方である。

**対処:** Test を即座に凍結。以後の意思決定は Train + Validation のみ。
最終判定は未使用の期間（2026-08-15 以降のフォワード）か未使用の通貨で、1 回だけ。

## 3-2. C 査読（adversarial-reviewer）が一度も入っていない

`research/EXP-FX000005/` に査読成果物が存在しない（`research/_templates/review.template.md` は
あるが未使用）。6 回の改善ループすべてが **S（司令塔）↔ A/B の往復**である。

CLAUDE.md の採用ゲート「C の採用可 + 人間の GO」が、採用側でも不採用側でも機能していない。
本レビューで挙げた F1〜F3 は、まさに C の守備範囲（楽観結果を割りにいく）で見つかるはずのものだった。

**対処:** 「機械的には REJECT 相当だが未練がある」局面こそ C を必ず通す運用にする。

## 3-3. 基準が結果を見た後に動いた事例が複数ある

| 変更 | タイミング | 影響 |
|---|---|---|
| DD 定義（初期資金比 → ピーク比） | 初期資金比で FAIL を見た後 | Test 4/10 → 5/10 |
| コストモデル（TP 指値化） | Train マイナスを見た後 | Train +372% → +444% |
| コストモデル（SL / トレール指値化） | 同上 | Train +444% → +530% |
| TP3 3R → 4R | Train 反実仮想スイープ後 | 質的改善 |
| EUR/USD 除外 | Train 単独結果のみ | **適切** |

CLAUDE.md の「A 設計は数値を動かさず、基準を動かす**前に**固定」に照らすと、
`00-spec.md` が append-only の意思決定ログ化し、
**事前登録（spec）と事後記録（result）が同じファイルで混ざっている**のが構造的な原因である。

**対処:**
- `00-spec.md` は凍結する
- 変更は `00-spec-amendment-NN.md` として積む。各改訂に
  「日付 / 理由 / **結果を見る前か後か** / 影響を受ける過去の判定」を必ず書く
- `01-trade-scenario-definition.md` を切り出したのは正しい方向。さらに進めて、
  定義書は**実装から自動生成またはテストで実装と突き合わせる**（F1・F3 のような乖離を防ぐ）

## 3-4. 多重検定の回数が数えられていない

司令塔の設計変更指示（ダウ理論連続エントリー / 1 通貨 1 ポジション / H1 継続確認再開 / SL 指値化）が、
そのまま設計変更として直入りしている。人間の直感を入れること自体は良いが、
**改善が出た変更ほど後付けで正当化されやすい**。

現時点で少なくとも十数回の試行を経ているため、Train Sharpe 1.799 という数字は相応に割り引く必要がある。

**対処:** 試行回数の一覧表を作り、**Deflated Sharpe Ratio**（Bailey & López de Prado）または
**SPA テスト**で補正した値を併記する。

## 3-5. 停止条件がない

SYS-FX008 には「改善ループ 3 試行で停止」という条件があったのに、SYS-FX011 は第 6 試行まで来ている。
また判断のたびに「司令塔判断待ち」で止まる構造は、
CLAUDE.md の運用方針「モバイルからの指示が多いため、ユーザのオペレーションは最低限に」と合っていない。

**対処:** 起票時に「改善ループは N 回、超えたら自動 REJECT」を事前登録する。

## 3-6. 記録の整合性（軽微）

- `research/EXP-FX000005/10-result/` にはパラメータ JSON 1 件のみで、
  実験結果は `research/method-notes/` 側に置かれている。
  他の EXP（EXP-FX000001 等）は `10-result/` に結果を集約しており、規約が揺れている。
- `10-result/run.log` が `.gitignore` の例外として追跡必須とされているが、EXP-FX000005 には存在しない。

## 3-7. 評価すべき点

以下は維持・横展開すべき良い実践である。

- HARKing 防止のため選定を Train 単独に限る運用（EUR/USD 除外、感度分析 Part A/B とも徹底されている）
- バグ発見時に「過去の全結果への影響」を明記する姿勢（`simulate_scaled_scheme` の exit_time 逆転バグ）
- 限界の明記（「予定外の地政学ショックはカレンダーでは原理的に防げない」）
- 自分の誤りを撤回・訂正する記録（DD 定義の取り違えを「誤りだったと判明・訂正する」と明記）
- `ACTIVE.md` / `portfolio-ledger.md` / `SYSTEMS.md` の役割分離と整合性
- 改善案を単独・組み合わせで切り分けて比較する手続き（第 5 試行の変種比較）

## D. 最大連続損失の帰無分布（2-2）

```python
import numpy as np
rng = np.random.default_rng(0)
def maxrun(n, p_win, reps=3000):
    out = []
    for _ in range(reps):
        x = rng.random(n) >= p_win      # True = loss
        m = c = 0
        for v in x:
            c = c + 1 if v else 0
            m = max(m, c)
        out.append(m)
    return np.mean(out), np.mean(np.array(out) <= 5)

for name, n, w in [('Train', 345, 0.638), ('Validation', 104, 0.55), ('Test', 173, 0.58)]:
    mean, p_le5 = maxrun(n, w)
    print(f'{name}: 期待値={mean:.2f}  「≤5」に収まる確率={p_le5:.1%}')
```
