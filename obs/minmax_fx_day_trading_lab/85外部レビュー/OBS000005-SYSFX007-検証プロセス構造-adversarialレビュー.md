## 反論（不採用の論点）

### 論点 A: 判定エンジンが存在するのに使われていない
`decision/criteria.py` は K1m〜K7m の閾値・Day30/60/90 ゲートまで実装済みだが、実際の合否判定はすべて人間がその場で Markdown に書いたラベルで行われている。コード化された基準がある以上、それを経由しない判定は「基準を試算前に数値で固定する」という spec の大原則（HARKing 防止）を担保できない。**判定エンジンを迂回して人力で判定を書けてしまう運用そのものが穴**である。

### 論点 B: 改善ループが「止まる条件」を持たない
Base → A1 → A2 → A1+A2 → A3 → A4 という流れは、どのステップも「ダメだったので次の変数を変える」という反応的な意思決定であり、**事前に「この N 個の仮説を試してダメなら SYS-FX007 は REJECT で確定」という停止条件が定義されていない**。現状のままでは、理論上ずっと新しいプリセットを追加し続けられる（実際 §11.7 で早くも次が 4 件積まれている）。これは典型的な「researcher degrees of freedom」であり、十分な試行回数をかければ見かけ上良い結果に到達すること自体は驚くべきことではない。

### 論点 C: spec のプロトコルを守らずに single-year でチューニングし続けている
spec が定めた train/validation/test の 3 分割は、まさに本書が指摘する問題（同一データへの繰り返しチューニング）を防ぐための仕組みである。にもかかわらず、実際の検証はすべて 2024 単年に対して行われており、**spec 自身が用意した防波堤が一度も機能していない**。

### 論点 D: 「同じ失敗パターンの 3 回連続」が打ち切りサインとして扱われていない
A1+A2・A3・A4 の 3 プリセット全てで「守り改善・攻め悪化」という同一の失敗構造が再現されている（OBS000003 §8.5, §9.5, §11.6）。これは「決済パラメータやフィルターをどう調整しても、エントリーそのものにエッジがない」ことを強く示唆する統計的シグナルだが、現在のプロセスはこれを「次の変数を試すべき理由」としてしか扱っておらず、「これ以上パラメータ調整では解決しない」という結論に到達する仕組みがない。

### 関連: OBS000006（パラメータ基準値の根拠レビュー）

「次の一手（グリッドサーチ拡大）への歯止め」という論点をさらに掘り下げ、**そもそも現行パラメータの初期値・デフォルト値自体が実データ分析ではなく一般的なテクニカル分析の慣例値（ATR(14)・Donchian(20)・SMA(20/50/200)・ADX 閾値等）に基づいている**という問題を `OBS000006-SYSFX007-パラメータ基準値の根拠-adversarialレビュー.md` として別途起票した。グリッドサーチを広げる前に、まずデータ分析に基づくパラメータ再設計（Train データの ATR・レンジ分布からの基準値導出）を行うべき、という具体的な差し戻しを提示している。

### 新たな懸念: 次の一手が「グリッドサーチ拡大」に向かっている

TVT 完了後の引き継ぎノート（`20260814-引き継ぎ-OBS000004-TVT完了.md`）は中期検討として「①根本見直し（平均回帰/ブレイクアウト系の再設計）②パラメータ拡張（より広いパラメータ空間でのグリッドサーチ）③通貨特性合わせ込み」を挙げている。②「パラメータ拡張」は、**本レビューが問題視した『負けるたびに次の変数を試す』ループそのものに戻るリスクがある**。今回は train/val/test を使って「エッジがない」という結論に到達できたが、次にグリッドサーチを広げる際は:

1. 事前に探索するパラメータの組み合わせ数と試行回数の上限を明記する
2. 探索は必ず train データのみで行い、validation/test には**候補が固まってから 1 回だけ**触れる（spec の「段階的絞り込み」に立ち返る）
3. permutation test・多重比較補正を先に実装してから広域探索に着手する

という順序を踏まないと、「多くのパラメータを試したら 2024 年の AUD/JPY のような偶然の当たりが再び出る」という同じ罠を、通貨軸からパラメータ軸に移しただけで再演することになる。**差し戻し項目としては未解消のままだが、直近のプロセス運用としては前進**と評価する。

### 差し戻し5（permutation test）: 実装完了、方式は簡略化

`src/minmax_fx_dt/backtest/permutation.py` を新設し、トレード損益列に対する符号シャッフル permutation test（1000回、spec既定）を実装した。**方式は spec 文言（「ラベルシャッフルでエンジンをフル再実行」）から簡略化**している: 1セルのバックテストが数百秒かかるため、1000回のフル再実行は現実的な計算コストを超える。代わりに、既に確定したトレード損益列の符号を50%でランダム反転させる sign-flip 検定を採用した。これは「観測された勝敗方向がコイン投げで説明できるか」を検定するもので、真のラベルシャッフル（エントリー条件自体を乱数化して再実行）より弱い検定だが、サンプル数不足を機械的に可視化できる。方式選択の詳細は `permutation.py` のモジュール docstring に記載。実際に AUD/JPY test 期間（n=7）で試算したところ p=0.781（有意差なし）となり、既知のサンプル不足と整合する結果が得られた。

多重比較補正（Bonferroni 等、差し戻し5後半）は今回未着手。5通貨×3期間=15セルに対する補正は次回 TVT 再実行時の課題として残る。
