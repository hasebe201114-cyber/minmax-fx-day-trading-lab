# OBS000005 - SYS-FX007 検証プロセス構造に対する Adversarial レビュー

> 担当: C 品質チーム（adversarial-reviewer 視点、司令塔依頼によりチャットセッションで代行起票）
> 起票: 2026-08-14
> 対応 OBS / 検証: OBS000003 §8〜11（パラメータ・アブレーション全般）、OBS000004（AUD/JPY 個別判定）
> 対応 SYS: SYS-FX007（レンジブレイク・プルバック戦略 v2）
> 方針: 良好結果を積極的に疑う。楽観バイアスの最終砦。**本判定書は個別通貨・個別プリセットの数値ではなく、検証プロセスそのものの構造的健全性を対象とする。**
> 前提: OBS000004（AUD/JPY 採用候補の個別判定、判定: 保留）とは論点を分離。本書は「合否判定の下し方」「改善ループの回し方」という**プロセスレベルの欠陥**を扱う。

## 最終判定

- [ ] 採用可

個別戦略（AUD/JPY 等）の採用可否ではなく、**「現在の検証プロセスの運用方法」自体が spec の設計思想（HARKing 防止・段階的絞り込み・train/validation/test 分離）から逸脱しており、このまま同じやり方で試行を重ねても信頼できる採用判断に到達しない**、という判定。プロセスを是正した上での再走行を要求する。

## 背景（レビュー対象）

OBS000003 §8〜11 にかけて、USD/JPY 単年（2024）データに対して Base → A1_SL_TP → A2_Donchian50 → A1_A2_combined → A3_ADX30 → A4_PullbackDepth の 6 プリセットが順次試行され、続いて A1_A2_combined を 5 通貨に適用する通貨ピボット（B1）が実施された。この一連の進め方（「ダメだった変数を 1 つ変えて再挑戦」を繰り返すループ）が、spec (`research/EXP-FX000001/00-spec.md`) および運用計画 (`research/ACTIVE.md`) が定めた検証プロトコルと整合しているかを検証する。

## 反論（不採用の論点）

### 論点 A: 判定エンジンが存在するのに使われていない
`decision/criteria.py` は K1m〜K7m の閾値・Day30/60/90 ゲートまで実装済みだが、実際の合否判定はすべて人間がその場で Markdown に書いたラベルで行われている。コード化された基準がある以上、それを経由しない判定は「基準を試算前に数値で固定する」という spec の大原則（HARKing 防止）を担保できない。**判定エンジンを迂回して人力で判定を書けてしまう運用そのものが穴**である。

### 論点 B: 改善ループが「止まる条件」を持たない
Base → A1 → A2 → A1+A2 → A3 → A4 という流れは、どのステップも「ダメだったので次の変数を変える」という反応的な意思決定であり、**事前に「この N 個の仮説を試してダメなら SYS-FX007 は REJECT で確定」という停止条件が定義されていない**。現状のままでは、理論上ずっと新しいプリセットを追加し続けられる（実際 §11.7 で早くも次が 4 件積まれている）。これは典型的な「researcher degrees of freedom」であり、十分な試行回数をかければ見かけ上良い結果に到達すること自体は驚くべきことではない。

### 論点 C: spec のプロトコルを守らずに single-year でチューニングし続けている
spec が定めた train/validation/test の 3 分割は、まさに本書が指摘する問題（同一データへの繰り返しチューニング）を防ぐための仕組みである。にもかかわらず、実際の検証はすべて 2024 単年に対して行われており、**spec 自身が用意した防波堤が一度も機能していない**。

### 論点 D: 「同じ失敗パターンの 3 回連続」が打ち切りサインとして扱われていない
A1+A2・A3・A4 の 3 プリセット全てで「守り改善・攻め悪化」という同一の失敗構造が再現されている（OBS000003 §8.5, §9.5, §11.6）。これは「決済パラメータやフィルターをどう調整しても、エントリーそのものにエッジがない」ことを強く示唆する統計的シグナルだが、現在のプロセスはこれを「次の変数を試すべき理由」としてしか扱っておらず、「これ以上パラメータ調整では解決しない」という結論に到達する仕組みがない。

## 差し戻し（該当あり）

- 差し戻し先: **S 戦略チーム（chief-strategist）+ A 設計チーム（strategy-architect）**
- 内容（プロセス是正の必須条件、優先順）:
  1. **`decision/criteria.py` を実際のバックテスト評価パイプラインに接続する**（`ablation_sweep.py` の出力を `evaluate_kpis()` に通し、判定を人力ラベルからコード生成に切り替える）
  2. **改善ループの停止条件を今から明文化する**: 「あと何プリセットまで試して基準未達なら SYS-FX007 は REJECT 確定」という上限を、これ以上試行を追加する前に数値で決める（事後決定は HARKing になるため、今すぐ・結果を見ずに決める）
  3. **spec 記載の train (2020-2022) / validation (2023-2024.6) / test (2024.7-2025.12) を実行する**。2024 単年でのプリセット追加は凍結し、まず現時点のベストプリセット（A1+A2 または A4）を validation 期間で 1 回だけ評価する
  4. **段階的絞り込み（train 上位 0.1% → validation 50 候補 → test 10 候補）を計画通り実施**するか、実施しないなら spec のその記述を「本 PJ では省略し単純な逐次探索を採用する」と明示的に修正する（暗黙の逸脱を止める）
  5. **permutation test（1000 回、p < 0.05）を多重比較補正込みで実装**し、現在までの全試行（6 プリセット × 5 通貨）に対して事後的に補正を適用した上で、AUD/JPY の優位性が統計的に有意か再確認する
  6. **DATA-FX001（DS-7 スワップ、DS-8 注文板）を先に完了**させ、Phase 順序（DATA → prescreen → spec → backtest）を spec 通りに戻す
  7. 上記 1〜6 完了後、初めて「AUD/JPY 採用候補」の再評価に着手する（OBS000004 の保留解除条件と合わせて実施）
