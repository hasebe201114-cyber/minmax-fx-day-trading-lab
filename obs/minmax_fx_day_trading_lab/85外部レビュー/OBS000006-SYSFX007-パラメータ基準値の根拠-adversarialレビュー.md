# OBS000006 - SYS-FX007 パラメータ基準値の根拠に対する Adversarial レビュー

> 担当: C 品質チーム（adversarial-reviewer 視点、司令塔依頼によりチャットセッションで代行起票）
> 起票: 2026-08-14
> 対応 OBS / 検証: OBS000003（全パラメータ・アブレーション）、OBS000004（AUD/JPY 個別判定）、OBS000005（検証プロセス構造）
> 対応 SYS: SYS-FX007（レンジブレイク・プルバック戦略 v2.1）
> 方針: 良好結果を積極的に疑う。楽観バイアスの最終砦。**本判定書は、既存の判定（不採用）そのものではなく、「不採用と判定する根拠になったパラメータ基準値が、実データ分析ではなく一般的なテクニカル分析の慣例値に基づいている」という前提の妥当性を扱う。**

## 最終判定

- [ ] 採用可
- [ ] 不採用
- [x] **保留（現行の「不採用」判定の解釈に留保が必要）**

OBS000004・OBS000005 で確定した「SYS-FX007（現行パラメータ）は不採用」という判定自体は覆らない。しかし、**その不採用が「戦略コンセプトにエッジがない」ことの証明なのか、「基準値の当てはめが実データの尺度に合っていないだけ」なのかを、現状のプロセスでは区別できない**。この論点が解消されるまで、「SYS-FX007という戦略アイデアそのものを見切る」という解釈には保留を付す。

## 背景（レビュー対象）

司令塔より「戦略で利用している各種基準値（ATR値・時間足など）が、取得した基準データをもとにした傾向分析の結果として設定されているか、それとも仮置きの基準に対して結果がダメだったから不合格としているだけではないか」という懸念が提起された。本書はこれを検証する。

## 反論

### 論点 A: 「不採用」は戦略コンセプトの否定ではなく、1 パラメータセットの否定に過ぎない
OBS000004・OBS000005 で確定した TVT 15 セルの不採用判定（AUD/JPY Test: PF 0.293, シャープ -2.054 等）は、**A1_A2_combined という 1 つの固定パラメータセット**についての結果である。このパラメータセット自体が「教科書の定番値を機械的に当てはめただけ」であるため、**戦略コンセプト（LT方向 + MTレンジブレイク + ST戻り確認）にエッジがないのか、基準値の当てはめ方が悪いだけなのかを、今回の不採用判定だけでは切り分けられない**。

### 論点 B: EUR/USD の全敗はこの問題の実例そのもの
EUR/USD の SL がノイズ幅と同水準で機能しなかった件は、「実データの尺度を見ずに一般的な倍率を当てはめた結果、構造的に機能しない設定になっていた」ことを如実に示す。同種の、目に見えにくい形でのミスマッチ（例えば GBP/JPY の ADX 30 という閾値が、GBP/JPY の実際のトレンド強度分布のどのパーセンタイルに相当するのか、検証されていない）が他の通貨・他のパラメータにも潜んでいる可能性がある。

### 論点 C: 「試行錯誤」と「データに基づく設計」は別物
Base→A1→A2→A3→A4 の一連の調整は、結果を見てから次の一手を選ぶという意味で OBS000005 が指摘した「改善ループに停止条件がない」問題と表裏一体だが、根はより深い。**そもそも初期値が実データ分析に基づいていないため、「次はどの方向に動かすべきか」の判断材料も勘に頼らざるを得なくなっている。** EDA があれば「ADX 30 は GBP/JPY では上位5%にしか該当せず、シグナルが出なくて当然」といった定量的な事前予測ができたはずだが、それがないため「守りが良くなった/攻めが悪くなった」という結果論の後追いに終始している。

## 差し戻し（該当あり）

- 差し戻し先: **A 設計チーム（strategy-architect）+ B 実装チーム（quant-researcher）**
- 内容（次のTVT/グリッドサーチ拡大に着手する前に実施すべき、優先順）:
  1. **通貨ペア別・時間軸別の基礎統計を算出するスクリプトを新設**し、Train データ（2020-2022、spec のプロトコルに準拠）のみを対象に:
     - ATR の実効 pips 分布（パーセンタイル、通貨ペア別 × 時間軸別）
     - レンジ幅・レンジ継続期間の分布（Donchian ブレイク頻度との関係）
     - ADX・トレンド強度の分布（「強いトレンド」を統計的に定義）
     - M5 バーの典型的な値動き幅（ノイズ床）と ATR の比率（EUR/USD 型のスケールミスマッチを事前検知）
  2. **上記の分布から、SL/TP/Donchian期間/ADX閾値をパーセンタイルベースで再設計**する（例: 「SL = 直近 1 年の該当通貨ペア ATR の中央値 × N」「Donchian 期間 = レンジ継続期間の 75 パーセンタイル」等）。固定倍率ではなく、通貨ペアごとに異なる値になることを許容する
  3. **再設計後のパラメータで Train データのみ再評価**し、明らかに機能しない通貨・時間軸を Validation に進める前に足切りする（spec の「段階的絞り込み」に相当）
  4. 上記を経た上で、初めて Validation → Test（TVT）を再実行し、**「データに基づいて設計されたパラメータでも不採用」という結果が出て初めて、戦略コンセプト自体を REJECT する**（この段階で REJECT なら、OBS000004/005 の不採用判定はコンセプトレベルの否定として確定してよい）
  5. 1〜4 は OBS000005 で提言した「次の一手（グリッドサーチ拡大）への歯止め」の具体的な実施内容として位置づける（無秩序な多変量探索ではなく、データ分析 → 仮説駆動の再設計という順序を踏む）

## 結論

現時点の「不採用」判定を覆す根拠はまだない。しかし、**この不採用が「戦略コンセプトの死」なのか「教科書的デフォルト値の当てはめミス」なのかは、現状の検証プロセスからは判別できない**。司令塔の懸念は妥当であり、次に着手する場合は上記差し戻し 1〜4（データ分析に基づくパラメータ再設計）を経てから、コンセプトの最終可否を判断することを推奨する。

## 追記（2026-08-14）: 差し戻し 1〜4 の具体的実施手順

差し戻しの実施方法について司令塔から具体案の提示を求められたため、以下の Phase 0〜5 に分解する。**最重要の安全策**: 統計量から基準値を導出する「ルール（数式）」は結果を見る前に固定し、事後的にバックテスト結果を見てから係数を選び直すことを禁止する（これをやると HARKing がパラメータ導出の 1 段階手前に移動するだけになる）。

### Phase 0: スコープ

- 対象データ: `data/curated/ds-1.json` のうち **Train データ（2020-01-01〜2022-12-31）のみ**（spec のプロトコルに準拠、Validation/Test は覗かない）
- 対象: 5 通貨ペア × LT(D1)/MT(H4)/ST(M5) の各時間軸

### Phase 1: 基礎統計スクリプトの新設

新規スクリプト `scripts/analyze_market_characteristics.py` を作成し、通貨ペア別に以下を算出する。

| # | 統計量 | 目的 |
|---|---|---|
| 1 | H4 ATR(14) の分布（中央値・25/50/75/90 パーセンタイル、pips 換算） | SL/TP の基準値算出 |
| 2 | **M5 バーの高安差（ノイズ床）の分布**（中央値・95 パーセンタイル、pips 換算） | EUR/USD 型のスケールミスマッチを事前検知 |
| 3 | Donchian チャネル内での価格滞留期間（ラン長）の分布 | Donchian 期間の妥当な長さを推定 |
| 4 | ADX(14) の該当ペア自身のヒストグラム | 「強いトレンド」を絶対値でなく相対値で定義 |
| 5 | ブレイク後フォロースルー率（ブレイク後に X×ATR 以上動いた割合） | false breakout 率の実測、RR 設計の根拠 |

出力: `data/curated/pair_characteristics.json`（通貨ペア別統計サマリ）

### Phase 2: パラメータ導出ルールの定式化（結果を見る前に確定）

ルール自体は **全ペア共通** にし、通貨ごとの数値だけが変わる設計にする（個別最適化すると通貨間の多重比較問題が再燃するため、OBS000004/005 の論点と一貫させる）。

```
SL_pips(pair)          = max(k1 × ATR_median(pair), k2 × noise_p95(pair))
Donchian_period(pair)  = round_to_standard(median_range_duration(pair))
ADX_threshold(pair)    = percentile(ADX_dist(pair), 70)
TP_pips(pair)          = SL_pips(pair) × RR   # RR はフォロースルー分布から一つだけ決める
```

`k1`・`k2`・パーセンタイル値（70 等）は、**本追記の時点で数値を仮決めしてコミットし、Phase 4 の結果を見てから変更しない**運用とする。

### Phase 3: プリセット自動生成への組み込み

`pair_characteristics.json` を読んで通貨ペアごとのプリセットを自動生成する関数を追加し、`ablation_sweep.py` / `run_train_val_test.py` の `MTFConfig` にそのまま渡せる形にする。「Base」「A1」のような手動プリセットではなく、`--auto-derive` のような 1 モードとして実装する。

### Phase 4: 再検証（spec 準拠の順序を厳守）

1. 導出したパラメータで Train データのみ再評価 → 明らかに機能しない通貨・組み合わせをここで足切り（段階的絞り込み）
2. Validation を **一度だけ** 実行
3. Test を **一度だけ** 実行
4. permutation test（未実装、これも合わせて実装）で統計的有意性を確認

### Phase 5: 最終判定

- これでも不採用なら、「コンセプトの死か当てはめミスか」という本レビューの疑問が解消され、**「戦略コンセプトの死」と確定してよい**
- 通れば、OBS000004 の残る差し戻し（両建てロジック統合・K7m 実測、ATR SL のスケール依存の再検証）に進む

### 実施順序の提案

Phase 1（統計量算出スクリプト）のみを先に実装し、通貨ペア別の統計量を一度提示してから Phase 2 のルール（k1・k2 等の具体的な数値）を確定する、という段階的な着手を推奨する。
